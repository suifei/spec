### 1. 项目目的(用户的根本意图 / 一切设计的约束)
`/spec` 是**过程管理的收口闸**。场景:团队成员用 AI 工具开发项目,用户在闸口**收口三类产出价值**:
1. **项目初期的 spec 规格说明书**(由 `/spec` 产出)
2. **项目源代码与文档等产物**(下游执行产出,解耦)
3. **从项目中提取的 skill**(沉淀复用,解耦)

**铁律:spec 没建立好,就不能施工。** 唯一例外:必须依赖前序阶段成果才能推进的研究型阶段(阶段化)。
→ `/spec` 负责价值①,并为②③把关;②③本身与 `/spec` 解耦,由下游执行,只读 `CLAUDE.md` → `SPEC.md`。

### 2. 此前已积累的设计决策(回顾)
- **D1** `/spec` 是单一、可重复执行的命令,精神类似 `/init`,但面向"活的规格书"。[已定]
- **D2** 固定产物 `SPEC.md` 置于仓库根,整文件重写,不碎片化。[已定]
- **D3** `CLAUDE.md` 顶部声明 `SPEC.md` 为最高优先级权威。[已定]
- **D4** 与执行解耦:`/spec` 只定规格、验就绪,不写产品代码。[已定]
- **D5 摸排探真**:每个"真实源/门"必须由**真实可执行探针**验证(非 AI/人口头判定);**没有绿灯探针就不算关、就不许施工**。[已定]
- **D6 探针可信约定**:严格退出码、打印原始证据、反向对照、无密钥、记录在哪台机器何时跑;非破坏自清理,危险动作先确认;诚实标注"只证明此机此刻"。[已定]
- **D7 阶段化**:探不了的真相归入后续阶段;此前我把它设计成了"一等公民的阶段状态机"(依赖图、延期门触发器、locked/provisional 标签)。[**本轮被质疑是否过度设计**]

### 3. 本轮输入 · 逐句记录与我的理解
> 用户原话拆解为原子点 A–P;每点含【原意】(我对这句话的解读)与【我的理解/推论】。

- **A.「回到之前的问题——当一个项目要划分多个阶段」**
  - 原意:把话题拉回"多阶段项目"这个场景。
  - 我的理解:这是要重新审视 D7(阶段化)的设计是否合理。

- **B.「`/spec` 是不是应该最小化设计,像 1 个函数,功能单一,但可被人类重复利用」**
  - 原意:主张把 `/spec` 设计成**最小、单一职责、可被人反复调用**的"函数",而非庞大系统。
  - 我的理解:Unix 哲学——do one thing well。把复杂度移出工具本身。

- **C.「在 1 阶段执行就是 1 阶段,到 2 阶段执行就是 2 阶段」**
  - 原意:**"当前是第几阶段"由人在何时调用来决定**,工具不自己维护阶段状态机。
  - 我的理解:阶段推进权在人手里;`/spec` 每次只对"此刻的当前阶段"工作。工具是无状态/弱状态的,人是调度器。

- **D.「这样不引入更复杂的控制」**
  - 原意:避免在工具里堆叠复杂控制逻辑(依赖图、自动触发等)。
  - 我的理解:直接对应、并倾向**否定 D7 的重型阶段状态机**。

- **E.「我们关注一件事:把当前阶段的 spec 制定好」**
  - 原意:`/spec` 的单一职责 = 把**当前阶段**的规格做扎实(脑暴→决策→探真→落档)。
  - 我的理解:"当前阶段"是工具的工作单元;不操心全局编排。

- **F.「我们只解决 1 个问题:不能覆盖上个阶段制定的 spec 即可」**
  - 原意:跨阶段唯一的硬约束 = **不得覆盖/推翻已封存的上一阶段 spec**(追加,不清洗)。
  - 我的理解:这条**取代**了 D7 里复杂的 locked/provisional/触发器机制——简化为一句不变量:**已封存阶段不可变,新阶段只追加**。这是整个简化方案的"锚"。

- **G.「从这个角度设计,实用性更强」**
  - 原意:最小化 + 单一不变量,实用性优于复杂编排。
  - 我的理解:认同。复杂编排的维护成本/认知负担高,且容易与"人驱动"的现实脱节。

- **H.「从人类角度:始终只需在必要时刻用 `/spec` 来下达/更新/总结」**
  - 原意:人对 `/spec` 的使用就三种时机:**下达**(立新)、**更新**(改)、**总结**(收口)。
  - 我的理解:一个入口、三种意图,工具按意图自适应,但对外只有 `/spec` 一个动作。

- **I.「这样就自动进入脑暴和决策流程」**
  - 原意:一调用 `/spec`,就自动进入"脑暴 + 决策"的固定流程。
  - 我的理解:`/spec` 的核心体验 = 进入一个**固定的脑暴/决策协议**,而非填表。

- **J.「加强一个要求:脑暴决策时,AI 是超级知识拥有方,人类具有决策权」**
  - 原意:明确**分工**——AI 出知识,人拍板。
  - 我的理解:这是对脑暴循环的"宪法级"约束,必须固化进提示词。

- **K.「人类知识不能和 AI 比,但创造力、想象力、核心痛点洞察力是 AI 不具备的」**
  - 原意:界定**人类不可替代的价值**:创造力、想象力、对核心痛点的洞察。
  - 我的理解:循环必须**主动向人索取**这三样(尤其"核心痛点"),因为 AI 生成不出真正的痛点洞察。

- **L.「所以 AI 应:引导、辅助、提示、优化建议、多决策建议和对比分析」**
  - 原意:AI 在循环里的**固定动作集**。
  - 我的理解:这些是可枚举、可固化的"招式",应写成固定提示词模板。

- **M.「这些都应设计成固定的提示词,让 AI 启用洞察能力,充分发挥知识库优势」**
  - 原意:把上面的招式**固化为提示词脚手架**,稳定触发 AI 的深度能力。
  - 我的理解:不能靠模型随机发挥;要有确定性的"脑暴协议"模板,每次都执行。

- **N.「人类判断是模糊的,AI 精确地将人类判断分解后得出评估结论」**
  - 原意:AI 的关键职责 = **把人模糊的判断,分解成精确的子标准,再据此评估得出结论**。
  - 我的理解:这是"招式"里最有分量的一招——**模糊→结构化→量化评估**。例:人说"要快又便宜",AI 拆成可度量标准(延迟阈值/月成本/运维复杂度…),对各方案打分,给出结论供人拍板。

- **O.「先理解,不写代码,先记录设计思路 + 我每句话的意思 + 你的理解」**
  - 原意:本轮交付物 = **这份讨论记录**,不是代码。
  - 我的理解:即本文件。

- **P.「我们等同自己先做一轮脑暴和决策讨论」**
  - 原意:用 `/spec` 的方式来设计 `/spec`(自举/dogfood)。
  - 我的理解:本文件就是这一轮脑暴的产出;决策项见第 6 节,待人拍板。

### 4. 浮现的方向:最小化、单一职责的 `/spec`
**提案**:`/spec` = 一个"函数",单一职责 = **把当前阶段的 spec 做扎实**;跨阶段唯一不变量 = **不覆盖已封存的上一阶段 spec**;阶段推进由人通过"在合适时机再次调用 `/spec`"来驱动。

**对比分析(我的角色:给分析+建议,你拍板):**

| 维度 | A. 重型阶段状态机(现状 D7) | B. 最小单一函数 + 追加不变量(本轮提案) |
|---|---|---|
| 工具复杂度 | 高(依赖图/触发器/标签) | 低(只认"当前阶段"+"勿覆盖") |
| 阶段推进的驱动者 | 工具(自动重探/解锁) | **人**(按需再调用) |
| 认知负担 | 高 | 低 |
| 与"人驱动"现实的契合 | 一般 | **高** |
| 跨阶段安全 | 靠 locked/provisional 机制 | 靠"已封存不可变"一条铁律 |
| 失败模式 | 机制本身可能出错/僵化 | 简单到难出错 |
| 探针/摸排探真 | 保留 | **保留(不变)** |

**我的建议**:倾向 **B**。把 D7 的重型编排**降级**为:`SPEC.md` 顺序累积"阶段块",`/spec` 只对当前阶段工作并**视已封存阶段为只读**;不再维护自动触发器/依赖图。探真(D5/D6)完全保留。这更实用、更稳、更贴合"人是调度器"。

**保留 vs 收敛(若采纳 B)**:
- 保留:摸排探真、探针证据、"没绿灯不施工"、`SPEC.md`/`CLAUDE.md` 权威、三种使用时机。
- 收敛:删去"延期门自动触发器""阶段依赖图""locked/provisional 双标签",代之以**"阶段封存=只读,新阶段只追加"**。

### 5. 原则:脑暴循环中的 AI⇄人 分工(需固化为提示词)
**人类(决策权)**:创造力、想象力、**核心痛点洞察**。循环必须主动索取这三样。
**AI(超级知识)**:广度知识 + 精确分解。固定"招式":
1. **铺开选项空间**:把该问题已知的所有合理方案列出(发挥知识库广度)。
2. **对比分析**:方案 × 评价标准 的对照表。
3. **推荐 + 理由**:给出知识背书的默认建议。
4. **模糊→精确**(最关键):把人模糊的诉求**分解为可度量的子标准**,对方案打分,得出评估结论。
5. **暴露风险/边界/隐藏假设/盲区**。
6. **请人拍板**:把人放在决策位,AI 在分析位。
7. **探真验证**所选路径(摸排探真)。
> 这套"脑暴协议"应作为**固定提示词脚手架**写进 skill,每次调用必执行,而非靠模型临场发挥。

## 第 2 轮 · 2026-06-29

### 1. 关键澄清:闭环的定义 & 阶段是"涌现"的(而非预设)
- **闭环 = 决策全部确认 ∧ 真值源全部探真**。二者都确认,才算闭环。
- **一个闭环 = 一个阶段可推进 = spec 即算建立**。
- **阶段不是人类预先设定的,而是递进涌现的**:用户提出想法 → 若当前 spec(若已存在)无法满足 → 进入"脑暴 + 决策 + 真值源探真"流程 → 达成闭环 → 该闭环即被标记为新阶段(阶段 N+1)。**每达成一次闭环 = 诞生一个阶段。**
- 推论:`/spec` **无需把"阶段"当作要用户预先规划的东西**;阶段是流程的副产物。工具永远只关注"让当前这次诉求达成闭环"。

### 2. 决策锁定(Q1–Q5)
- **Q1 ✅** 最小化(封存只读 / 只追加,替代依赖图 + 触发器)。
- **Q2 ✅** 单文件 `SPEC.md`,顺序累积 `## 阶段 N` 块,旧块封存只读。
- **Q3 ✅** 阶段块带**状态标注**;**最后一个"未标注完成"的块即当前阶段**。
- **Q4 ✅** **绝对只读**;对已封存阶段有异议 → 不改旧块,而是走流程达成新闭环并标记为新阶段(新阶段须显式声明覆盖了旧结论的哪一条)。
- **Q5 ✅** **一个指令搞定**:不显式分模式;`/spec` 由状态自决(见下)。

### 3. 由此推出的单指令行为(状态自决,无模式)
读 `SPEC.md`:
- **无** → 新建,开"阶段 1",带用户想法进入 脑暴→决策→探真,闭环则封存阶段 1。
- **有,且存在"未完成"阶段块** → 那就是当前阶段,继续推进直至闭环。
- **有,且全部已封存,用户又带来新想法**:
  - 当前 spec 已能满足 → 明确告知"已满足,无需新阶段"。
  - 不能满足 → 开新阶段 N+1,脑暴→决策→探真→闭环→封存。
- "更新"落在当前未封存阶段 = 正常推进;指向已封存阶段 = 触发新阶段。
- "总结 / 收口" = **闭环达成那一刻自动封存当前阶段**,无需独立指令。
→ 下达 / 更新 / 总结 三时机,全部坍缩进"带想法调用 `/spec`"这一个动作。

### 4. 需保证的连贯性点(我的建议,待确认)
append-only 账本下,后阶段若推翻前阶段结论,**必须显式标注"本阶段 supersede 阶段 K 的某条"**,这样"当前生效的 spec"始终无歧义(读者顺着账本叠加,后者仅在显式声明处覆盖前者)。建议:把"supersede 引用"设为新阶段的**必填项——当且仅当它否定了旧结论**。

### 5. 闭环判定(操作化定义)
阶段 N 闭环 ⟺ 块内**每条决策都被人确认** ∧ **每个真值源/门都有绿灯探针证据**(或显式接受的弱证据 attestation)。满足 → 标记 `已闭环(sealed)` + 日期,转只读;否则保持"进行中",即当前阶段。

### 6. 状态
Q1–Q5 已锁定,设计基本收敛。**待你一声"开始落代码",我就**:① 把 SKILL 的阶段部分改为"涌现式阶段 + 封存只读";② 新增固定的"脑暴协议"提示词模块(铺选项→对比→推荐→模糊判断精确分解评估→风险→请人拍板→探真);③ 把 `SPEC.template.md` 改为"阶段块账本 + 状态标注 + supersede 引用"。

> **Q6 已确认**:新阶段推翻旧结论时,必须显式写 "supersede 阶段K 的第X条"(仅在确有否定时必填)。

## 第 3 轮 · 2026-06-29 — spec 的"层级"与 spec↔code 同步(防文档/代码漂移)

### 0. 问题(用户提出)
项目会反复改(UI 反复调、架构重构、实现微调、甚至 JS→Python)。担心:spec 太固定 →
文档与代码巨大偏差;但又不能限制代码改动。如何同步?spec 该约束到哪一级——产物级还是更细?

### 1. 核心结论:spec 只管"契约面",不管"实现内部"
存在一条 **spec 线**。线之上受 spec 治理;线之下是实现细节,自由变更,只需"保持 spec 的探针/验收为绿"。

- **线之上(进 spec;改它 = 新阶段 + 探真)**:可观察行为/能力 + 验收标准;契约/接口
  (API、数据格式、CLI、集成点);真值源/门 + 不变量;关键 NFR(可度量阈值);团队**显式
  声明锁定的约束**(如"必须 Python""必须离线",每条带理由)。
- **线之下(不进 spec;自由 churn;仅受"探针保持绿"约束)**:代码结构/模块文件布局/类设计/
  算法;UI 视觉设计(像素级);语言、库选择(**除非**被显式声明为门);重构;实现微调。

→ "约束到哪一级":**约束到产物的契约面,不更细。** 更细 = spec 变成代码副本 = 漂移源头。

### 2. 同步机制:让 spec 的边界"可执行",而非改 spec 去追代码
- 不靠人工 diff 文档 vs 代码。**spec 的验收标准与门 = 可在 CI 跑的探针**。
- 代码随便改;**任何时刻"是否同步" = 探针是否还绿**。重构破坏行为 → 探针变红 → 漂移被机器抓到。
- 即:**spec 是固定契约,代码在其下自由运行,探针是拴绳。自由在线下,纪律在线上。**
- 推论:**探针有双重身份** = 闭环时的"探真" + 之后 CI 里的"漂移检测/回归门"。

### 3. 判定工具:任何改动问一句——跨过 spec 线了吗?
它改变了 可观察行为 / 契约接口 / 真值源·门 / NFR阈值 / 已声明约束 吗?
- **否** → 线下 → 直接做;CI 探针守契约;不动 `/spec`、不产生阶段。
- **是** → 线上 → 先 `/spec` 达成新闭环(新阶段 + 探真)→ 再施工。"没准备好不施工"适用。
→ 同时回答了"先 spec 还是先重构"。

### 4. 场景模拟
| 场景 | 跨线? | 做法 | spec |
|---|---|---|---|
| UI 反复微调(布局/配色) | 否 | 直接改,行为探针保持绿 | 不动 |
| UI 改变了能力/流程 | 是 | 先 /spec 闭环再做 | 新阶段 |
| 纯重构(行为不变) | 否 | 重构,跑探针确认仍绿 | 不动 |
| 重构换了真值源/契约(数据模型迁 PG) | 是 | 先 /spec 重探新门再做 | 新阶段 |
| 实现微调 | 否 | 直接做,探针守门 | 不动 |
| JS→Python,语言非声明约束 | 否 | 重写,保持行为/契约探针绿 | 不动 |
| JS→Python,语言是声明约束 | 是 | 先 /spec 重定约束 + 探新栈 | 新阶段 |

### 5. "不断涌现阶段去适配代码"为何不对(用户直觉正确)
阶段由**意图/决策的改变**涌现,**不由代码改动**涌现。spec 引领,代码跟随。线下 churn 不产生
阶段;线上意图变才先闭环再施工。例外是**反馈路径**:实现中发现 spec 本身错了(探针绿不了/
决策不可行)= 一次"证伪",触发新阶段重决策——触发点是"发现/决策",不是"代码编辑"。

### 6. 谁画这条线
线不普适:库项目 API 即产物 → 契约写得细;内部工具 → 很松。**由用户(决策权)通过"声明什么
是门"来画线**;AI(分析方)负责**建议线画在哪**,并在条目"过细(引发 churn)"或"过虚(无法
验收)"时预警。

### 7. 对设计的影响(待确认后并入实现)
- 脑暴协议固定动作新增一条:**为每个拟入 spec 的条目判定"线上/线下";线下的劝退**(交给 CI
  探针守,不写进 spec)。
- 明确**探针双重身份**:闭环探真 + CI 漂移检测/回归门。
- `SPEC.template` 的验收/门 显式写成"可被 CI 复跑"的形式。

## 第 4 轮 · 2026-06-29 — 探针的"空洞绿"问题(probe vacuity)

### 0. 问题(用户提出)
此前探针多是"外部存储 / 外部依赖"。漏洞:若探针 = `npm run test`,而项目只写了最简单的恒绿
测试,则探真失去根本意义。且项目初期很难确定真测试,**此情形极易发生**。

### 1. 定性:探针分两类,洞在第二类
- **A 类·存在/环境**:X 是否存在/可达/可写。**自证型**,原始证据即事实,难以空洞(SQLite
  要么真写进要么没有)。此前例子全属 A,故显得稳。
- **B 类·行为正确性**:代码做对没有。价值**完全取决于断言了什么**。`npm run test` 的绿可以
  毫无意义。洞在此。Goodhart:一旦"绿"成施工门槛,就有动机造恒绿水灯。

### 2. 统一解药:无法"变红"的探针 = 空洞 = 不接受
把 A 类已用的反向对照(端口二次 bind、写不可写路径)升为**普适铁律**:任何探针都必须**演示
其失败模式**——对错误实现/变异版跑一遍**必须变红**;证据**同时展示"对→绿"与"错→红"**。
`npm run test` 对水测试恒绿、对错误代码也绿 → 无法变红 → 空洞 → 打回。

### 3. 具体规则
1. **禁止"跑整个测试套件"当门探针**;门探针必须对准 spec 的**具体 scenario(WHEN/THEN)**,
   断言具体输入→输出。
2. **探针源自 spec,不源自仓库已有测试**——独立于开发者的水测试;开发者 `npm test` 是其安全网,
   不是门。
3. **反向对照必填**;构造不出"红"的探针打回。
4. **证据展示断言本身**(具体期望值 + 反向对照结果),不只 "PASS"。

### 4. 早期项目:写不出真测试 = 门未闭(而非用假测试闭门)
此刻写不出有意义的行为断言 → 该行为**还没被规格化** → 门**保持开**(开放问题/后续阶段)。
早期合法可闭的是 A 类(环境/依赖/可行性);B 类门随 scenario 被钉死而逐步可闭。
**"写不出真测试" ≠ "用恒绿测试闭门",而 = "这个门还没闭"。** 契合"没准备好不施工"。

### 5. 诚实边界:探针只验"已声明之真"(洞只能堵一半)
- 单个探针的空洞 → 可堵(反向对照)。
- 是否探全(覆盖完备性)→ **不可证**。spec 只保证其**已声明、已探**的门;绿 ≠ 全局正确。
- **spec 是"已验证之真的下界",不是正确性证明。** 须如实标注,避免对绿色看板过度信任。

### 6. AI 固定动作升级:对抗式探针审查
脑暴协议新增:**AI 主动尝试"用错误代码骗过该探针";骗得过 = 空洞 = 打回。** AI 当自己探针的
对手(契合"AI 精确分解、暴露盲区"的分工)。

### 7. 对设计的影响(待并入实现)
- 探针规约新增:**反向对照为必填**;门探针必须引用其证明的 spec scenario;禁止裸跑测试套件。
- 闭环判定补充:**B 类门的"绿"仅在具备演示过的"红"时才计入闭环**。
- 脑暴协议补充"对抗式探针审查"步骤。
- 产物中如实标注"覆盖完备性不可证、绿≠全局正确"。

## 第 5 轮 · 2026-06-29 — 提示词合规 & spec 的管控层级

### A. 提示词必须符合 Claude 官方建议 + 专家角色(用户要求)
落码时每个 skill 提示词遵循 Anthropic 稳定的官方提示工程实践:
- **专家角色**(role prompting):"You are an expert systems analyst / spec author…"
- **清晰直接 + 显式**:明确说要做什么(4.x 模型按字面执行,忌空泛)。
- **给出 why/动机**(Claude-4 指南:陈述意图提升遵循度)。
- **XML 标签结构**(`<context>`/`<rules>`/`<steps>`/`<output>`)分隔指令与数据。
- **示例/multishot**,且示例与期望行为一致(好门、好探针、好 spec 块各一例)。
- **让 Claude 思考**(CoT):分析/分解步骤显式化(承载"模糊→精确评估")。
- **显式成功标准**:闭环门、绿探针门。
- **正向格式控制**(说该做什么,而非只说别做什么)。
- ⚠️ **不用 prefill**:末轮 assistant prefill 在 Opus 4.6+/4.8(Claude Code 运行的模型)会 400;改用 角色+XML+示例。
- (注:官方 prompt-engineering 文档被代理 403 挡住,以上为 Anthropic 稳定、已公开的实践;如需对照具体 live doc 可后续重试。)

### B. 管控层级:按"高度"定义,而非主题清单
- **OpenSpec 没有**多层级治理方案——它只到 需求(行为)+设计(技术)+任务(工作),单一高度、change 维度。无多视野规划、无痛点发现、无 ui/ux/运维专层、无 AI 主动真值源发现。所以本问题需从 spec 自身重新定义。
- **核心结论:问题不是"哪些主题",而是"每个主题进 spec 的高度"。** 每个主题都可进,但**只到 意图/契约/门 高度,绝不到实现细节**(= 第 3 轮的 spec 线)。

| 主题 | 进 spec 的高度 | 交给 AI 分解 |
|---|---|---|
| 需求痛点 | ✅ 愿景/why——**AI 主动洞察** | — |
| 技术架构 | 只到 真值源/门 + 契约 | 模块/文件/类布局 |
| UI/UX | 只到 能力/流程/体验约束 | 像素/配色 |
| 运维 | 只到 NFR/约束/门(SLO、部署目标) | 运维手册细节 |
| 输出成果 | ✅ 定义"完成产出什么"(三类价值) | — |
| 各种决议 | ✅ 决策日志核心 | — |

- **用户清单缺的两块**:① 每条的验收/探针(摸排探真层);② 显式 Out-of-scope。
- **"国家大计"类比**:在**高度**上成立(spec=大方向/目标/门;AI=职能部门自分解 HOW,spec 不微管)。差异:国家计划自顶向下预设 30/10/3 年;我们的阶段是闭环涌现。**综合 = 稳定"宪法层"(愿景+门+决策,极少变)+ 涌现"阶段账本"(每次闭环)**。不强切固定档;高度连续;铁律"spec 守高位、AI 分解低位、spec 不越位微管"。

### C. 真值源 = AI 主动洞察提炼(用户关键要求,采纳)
脑暴协议**第一步升级为"主动勘探(active reconnaissance)"**:用户贴 PRD / 指向仓库 / 给模糊诉求时,AI **主动读代码/文档/PRD、分析,主动提炼真正的痛点 + 候选真值源/门**,再与用户走 决策+探真 闭环。即 **真值源 = AI 发现 + 人类确认**,而非只靠人类申报。这是用户对 spec 的核心定义。

### D. 落码时并入
- 脑暴协议新增第 0 步"主动勘探";真值源候选由 AI 提炼、人确认。
- SPEC 模板:每个进 spec 的条目标注"高度"(意图/契约/门),线下项劝退;门带验收/探针;新增显式 Out-of-scope。
- 全程保持"spec 守高位、不微管"的硬约束。

## 第 6 轮 · 2026-06-29 — 核心诉求定调(设计定稿)

用户钉死核心诉求,并给出两个重要重定位。**这是验收标准。**

### 1. 真值源 = 人类决策前的"侦察兵"
AI 把勘探/发现/探真到的一切,作为**决策参考材料**交给人类;AI 跑腿取证呈现,人类拍板。
**取证求真(绝不造假)= AI 的纪律;施工放行(GO)= 人类的决策。** 默认仍是"没准备好
不建",但最终由人决定(可 override、可分阶段),不是机器冷硬挡住。
→ 这把"摸排探真"从"硬卡关卡"重定位为"为决策供证的侦察";探针/反向对照仍在,但其
**目的是给人类可信证据**,不是制造操作门槛。

### 2. 简单到不构成负担(一等需求)
一个 `/spec`,人类只管 **脑暴 + 决策**。**所有复杂机器(探针、阶段、高度判定、闭环判定)
藏在引擎盖下 = AI 的负担,不是人类的。** 不加操作负担,不加认知负担。
**严苛留给 AI 的内部纪律与取证,轻盈留给人类的界面。** 实现时人类面压到最简,机器面做厚。

### 3. 职责边界:/spec = Gate 1;skill-builder = Gate 2(Claude Code 内置)
- **Gate 1 = /spec**:产出一份*真正可行*的规格说明书并存档。
- **Gate 2 = skill-builder**:从项目提取 skill —— **Claude Code 已内置,不归 /spec 管**。
- → 之前列的"价值③ 提取 skill"移出 /spec 范围。/spec 专注 Gate 1。

### 4. 产物闭环
可行 spec → 存档(`SPEC.md`)→ AI 每次都用。**/spec 自动更新 `CLAUDE.md`:要求先读
`SPEC.md`,并置于 `CLAUDE.md` 顶部。**

### 5. 三类价值的归属(更新)
① spec 规格书 = Gate 1(/spec)产出;② 源码/文档产物 = 下游执行(读 CLAUDE.md→SPEC.md);
③ 提取的 skill = Gate 2(内置 skill-builder)。/spec 只负责 ①。

### 验收标准(实现必须满足)
- [ ] 利用 AI 优势 + 人类决策(脑暴 + 决策),AI 当侦察兵供证,人类拍板。
- [ ] 真值源由 AI 主动勘探取证后呈现给人类参考。
- [ ] 产出真正可行的 spec 并存档。
- [ ] 自动更新 CLAUDE.md:先读 SPEC.md、置顶。
- [ ] `/spec` 使用极简,不构成操作/认知负担。
- [ ] 定位为 Gate 1;不做 Gate 2(skill 提取)。

## 第 7 轮 · 2026-06-29 — 强化提问能力:"侦察→提问→决策"协议

用户要求加强 `/spec` 的提问能力,并给出参考:其"认知伴飞 (Cognitive Copilot)"设计文档
(Vibe Note)。**迁移其提问哲学到"访谈人类、逼出精确 spec"的目的;不搬其 PKM 专用机器。**

### 1. 硬顺序:侦察兵先考察,再提问(用户硬要求)
- **提问前必须先侦察取证**:读完用户指定要读的(PRD/仓库/文档/链接);搜自己的知识库;
  **该搜全网就搜全网**(答案取决于外部/最新事实:库、API、标准、先例)。能探真先探真。
- **绝不问本可自查到的东西。** 侦察完先呈现"我发现了什么(疑似核心问题、真实约束、候选
  真值源/门、风险、待决项)",**然后才提问**。

### 2. 提问目标:找到"核心问题"(非表层症状)
- **元问题先行**(Paul & Elder 第六类):"你要的 X,背后真正要解决的是什么?"
- **瞄准邻接信息差**(Loewenstein 倒 U):只问"有上下文但缺关键决策/事实"处;不问完全陌生
  的(激不起)、不问已定的(多余)。
- **六类苏格拉底问题**工具箱:澄清 / 探假设 / 探证据 / 另类视角(reframe) / 探后果 / 元问题。
- **反问 + 追问**:答案含糊或藏假设时顺着追。
- **视角翻转 + 类比迁移**:给没考虑过的角度——**邻接,不赌"意外相关"**(Kotkov)。

### 3. 风格约束(直接服务"不构成负担")
- **I-type 不 D-type**(Litman)、informational 不 controlling(SDT):"也许相关/要不要考虑",
  不用"你应该"。协同,不施压。
- **可应对性**(Silvia):每问自带足够上下文(为什么问 + 选项),不抛神秘概念。
- **按先验水平校准**(Khanmigo 教训):零基础→直接给建议+示例;中等→苏格拉底;高手→反事实
  追问。**检测到赶时间→给"直接说结论"档**。
- **低频**:一次只问"卡住决策"的一小批,不做问卷轰炸;被略过就退让。

### 4. 明确不迁移(避免把 /spec 做重)
ambient 投递、dismiss/snooze 持久化、认知拓扑三轴表、hedge 全库扫描、Learning-by-Teaching、
度量仪表板 —— 那些是 Vibe Note 产品机器;`/spec` 是交互式访谈,**迁移哲学,不迁移机器**。

### 5. 落码时并入(更新脑暴协议)
脑暴协议固定步骤变为:
0. **侦察**:读用户指定材料 + 搜知识库 + 必要时搜全网 + 探真取证。
1. **呈现侦察结论**:疑似核心问题 / 约束 / 候选真值源·门 / 风险 / 待决项。
2. **提问找核心**:元问题先行,瞄准邻接信息差,六类苏格拉底,reframe/类比,反问追问;
   I-type 措辞 + 可应对性上下文 + 按先验校准 + 赶时间给 direct 档。
3. **给选项 + 推荐 + 证据**,人类决策。
4. **探真验证**所选(侦察兵取证供决策)。
5. 闭环 → 写入/更新 SPEC.md。

## 第 8 轮 · 2026-06-29 — 侦察成果持久化(知识缓存)

用户补充:侦察(读材料+搜知识库+搜全网+探真)的发现**必须落地持久化、规范存储,避免下次
重复探索**。把"侦察"从一次性动作升级为可复用的知识资产。

### 1. 新增目录 `.spec/knowledge/`
每个主题/依赖一个规范 md。**侦察第 0 步先查此缓存**:命中且未过期 → 复用;只对缺口/过期项
联网探索。= 去重 / 避免重复探索机制。

### 2. 依赖选型标准流程(用户例子固化)
遇到外部依赖 → 搜该库 + 同类库 → 取 **稳定版 + 最新版 + 备选** → 给推荐 → **人类决策** →

### 3. 分工(高位决策 vs 低位知识)
- "用哪个库、钉哪个版本" = **决策** → 进 `SPEC.md`(决策日志 + 依赖门,高位)。
- 库的**详细知识/文档** → 进 `.spec/knowledge/<lib>.md`(低位细节),SPEC.md 引用它。
- 下游执行(写代码的 AI)读 `SPEC.md` + knowledge 缓存,**不重复联网**。

### 4. 规范文件格式
```
---
topic: <主题>
decision: <选定项 + 一句理由>
status: explored | decided | superseded
captured: <YYYY-MM-DD>
sources: [urls...]
---
## 候选对比   | 库/方案 | 稳定版 | 最新版 | 维护活跃度 | 备注 |
## 推荐       <推荐项 + 理由>
## 人类决策   <选定项 · 日期>
## 钉死知识(供执行)  关键 API / 坑 / 最小用法 / 文档链接
```

### 5. 新鲜度策略
带 `captured` 日期 + 版本。**默认复用**(用户目标=别重复探);仅当用户要求刷新、或 spec 改了

## 第 9 轮 · 2026-06-29 — 缺失闭环:断点续跑 / 状态外置(可靠性)

用户审计闭环,并提出长流程 + 200KB 上下文的可靠性担忧:AI 跑到一半上下文爆了/换会话,
还能记起自己在第几步吗?Claude Code 能可靠执行吗?

### 0. 闭环审计结论
其余闭环已齐(spec→码、码漂移→探针、决策→SPEC.md、侦察→knowledge、阶段→封存账本)。
**唯一缺口 = 进度持久化 / 可续跑**——正是本轮要补的。次要口子(漂移后重跑、Gate1→Gate2
交接)人工触发,可接受。

### 1. 核心原则:文件系统才是记忆,上下文是一次性的
**不靠上下文记住整个流程**(读一个仓库就可能爆 200KB)。**状态全部外置到磁盘**,每次 `/spec`
启动先从磁盘"复水"。

### 2. 新增进度账本 `.spec/STATE.md`(缺失闭环)
每次 `/spec` 第 0 步先读它重建状态;幂等、可续跑。格式:
```
# /spec 进度
updated: <时间>
current_phase: <N>
current_step: 侦察|呈现|提问|决策|探真|写入|闭环
core_problem: <目前理解的核心问题,一句话>
done: [...已完成,带产物指针...]
pending: [...开放问题 / 未探真的门 / 待侦察主题...]
next_action: <下一步唯一要做的事>
```
→ 换会话、compaction、上下文清零都不丢;再跑 `/spec` 读 STATE.md+SPEC.md+knowledge 索引,
报"我在第 X 步,已完成 A,接着做 B",续跑。

### 3. 控上下文预算(答"200KB 跑得完吗")
1. **侦察目标导向、有界**:只查"回答当前开放问题/钉当前门"所需,绝不读整库(呼应邻接信息差)。
2. **读完即压缩即遗忘**:重材料 → 提炼成 `.spec/knowledge/<x>.md` 小笔记 → 丢原文。
3. **重活交子代理**(Claude Code Explore/子 agent):读库、搜全网派给子代理,**只回摘要**,
   主循环不进原文。这是省主上下文的关键。
4. **每次调用只做一小块** → 持久化 → 可安全停;再喊 `/spec` 续。

### 4. 可见性
`/spec` 启动与每次暂停都报:当前步 / 已完成 / 待办 / 下一步。对人可见,对 AI 是续跑依据。

### 5. 可靠性诚实结论
- **能可靠执行——前提**:状态外置 + 重活交子代理。单次上下文只装"当前小块 + STATE.md 复水的
  摘要",200KB 够跑,任意时刻断了都能续。
- **不可靠——如果**一口气全装上下文(读整库、全程记心里)= 用户担心的失败模式。
- 本轮把设计从"假设一次性跑完"改为"分块 + 外置状态 + 续跑",可靠性从碰运气变结构保证。

### 6. 落码并入
- 协议第 0 步加"读 `.spec/STATE.md` 复水;若无则初始化"。
- 每完成一小块即写 STATE.md + 对应产物,再决定停或续。
- 重侦察(读库/搜网)用子代理,返回摘要写入 `.spec/knowledge/`。
- 启动/暂停时打印进度行。
- `.spec/STATE.md` 纳入提交(续跑依赖)。

## 第 10 轮 · 2026-06-29 — 时间维度(贯穿,但最小化)

用户要求加时间维度以区分新旧、全流程贯穿;但明确反对过度设计(砍掉新鲜度阈值/分级/格式花活)。

### 0. 直接结论
- **"新鲜度阈值"砍掉**:固定天数拍脑袋、不看语境(依赖最新版几天就旧、架构决策放半年还成立),
  只增维护负担,换不来准确判断。
- 收敛为两条:**① 所有记录都带真实时间戳(唯一硬约束);② 提示词教 AI 用判断理解时间。**
  不加新字段、不玩输出格式。

### 1. 取时间:调 OS 命令、跨平台、UTC、绝不臆造
- Unix/macOS/Linux/WSL/git-bash:`date -u +%Y-%m-%dT%H:%M:%SZ`
- Windows PowerShell:`(Get-Date).ToUniversalTime().ToString("yyyy-MM-ddTHH:mm:ssZ")`
- 模型一律从系统命令取时间,不凭记忆。**这是时间维度可靠性的命门。**

### 2. 理解时间:判断,不靠阈值
对比记录时间戳 vs 现在,**按事实性质 + 经过时长 + 世界是否可能变**判断是否过期(依赖"最新版"
老得快、架构决策老得慢、探针绿灯若被测对象可能已变就存疑)。默认复用;看着旧的提示人;要重核
需人点头或它在阻塞。输出标 recency(as-of / N 天前 / 已被替换)。

### 3. 落地(很轻)
- `SKILL.md`:新增"Time"段(两条硬约束 + 取时间命令 + 判断理解 + 标 recency + append-only 不改
  历史戳);Step 0 加"算 age、按判断提示陈旧",Step 6 加"戳真实 OS 时间"。
- `probes.md`:取时间改平台自适应 UTC、不臆造;gate 新鲜度由 evidence 时间戳派生。
- 三模板:统一措辞"真实 OS 时间(UTC)、不臆造";**不加任何新字段**(决策日期/门 Last-run/
  知识 captured/STATE updated/阶段 sealed 已覆盖时间)。

## 第 11 轮 · 2026-06-30 — 角色定位收口:需求收集专家;探真=研究;门要承重;少问多决

实现 v1 + 端到端测试(nebula-drift)跑完后,用户对**核心思想**做了关键澄清与补充。这一轮不是新增
机制,而是**校正定位**,把三处概念混淆/过度拘泥纠正过来,并明确 `/spec` 的本质角色。

### 0. 一句话定位(用户原话提炼)
`/spec` 就是让 AI 扮演**需求收集专家**,与用户一起收集需求:经 AI 思考或调查(外部工具、知识)把
用户**模糊的描述清晰化**,梳理并理解用户的想法,**提出更好的看法(建议、交互)**,向用户**报告哪些
没闭环(用户没想清楚)、哪些可落地(已闭环)**,最后**标准化**成 spec——确定**重点内容、边界、反
模式**。一个专家角色。

### 1. 探真 === 研究(纠正"把探真窄化为 check")
- **探真(探寻真相)与发现知识是同一件事**:用一切可用手段找真相——自身知识、全网、外部知识、
  用户线索、项目本地数据、skill、MCP,叠加深度推理与验算。
- **可执行探针只是其中一种手段**(对"环境/行为相关且承重"的真相,给最强证据),**绝不是探真的定义**。
  提示词不得把"探真"约束成"跑个检查脚本"。

### 2. 门(Gate)必须承重(纠正"端口探真这种常识也立门")
- 端口可绑、目录可写、工具在 PATH——这类**常识**毫无决策价值。**可以顺手探,但绝不能成为"门",更不
  能成为今后编码必须关注的重心**。我们不是围绕"端口是否可用"编程。
- **立门三准则(全满足才立)**:① 承重(真有决策/可行性系于它);② 不确定(可能为假);③ 错了有后果
  (改变设计而非实现细节)。原型是 nebula 里的 **G0**:推翻"原生构建"假设、改变方向——这才配做门。
- nebula 的 G1/G2/G3(node/端口/资源目录)正是被批评的"常识门",今后示例不再这么立门。

### 3. 少问多决:默认自决并登记,只上交两类(纠正"动不动让人决策")
- **默认**:AI 自己定,把**推演关键路径 + 结论**登记进 `SPEC.md`(决策日志),**无需人类决策**。
- **只在两种情况问人**:(a) **真不可达**——穷尽一切来源 + 深度推理后证据仍无法定夺(价值/优先级/风险/
  商业取向这类只有人能拍的叉),(b) **比人提的方案更好**——发现更优解,交人选。
- 常识、可推导的,一律不上交。

### 4. 落地(本轮改动)
- `SKILL.md`:开篇改为**"需求收集专家"角色 + 五步使命**(澄清模糊→梳理理解→提更好看法→报告闭环
  状态→标准化为含反模式的 spec);原则重写为"探真=研究 / 少问多决 / 门要承重 / 证据非杜撰";新增
  **"What earns a gate"** 三准则段;Step 1 更名"探真(=研究)"列全部手段;Step 2 增"闭环 vs 未想清"
  报告;Step 4 改"自决并登记,只上交真叉";Step 5 改"取证(承重门才探,常识不探)";Guardrails 同步。
- `probes.md`:开篇重定位"探针=探真的可执行一种";加"只为承重门写探针、常识不写";示例从"目录可写"
  (常识)换成"推翻假设式承重门"(GPU 假设 + 反向对照)。
- `questioning.md`:Rule 0 改为"调查→自决→只问两类叉"。

- `STATE.template.md`:步骤枚举 `探真(研究)|呈现|提问|决策|取证|写入|闭环`(取证=承重门取证)。

## 第 15 轮 · 2026-06-30 — `/spec` 产物对下游的价值;补 Gate 1.5(`/build`);仓库自举

### 1. 用户的疑问
"`examples` 都看了,不错。但这产物对后续开发的意义/价值是什么?没有真正的 PRD,AI 如何施工?
对产出 PRD 有价值么?PRD 会不会漂移?——不一定是 PRD,你怎么看?"

### 2. 我的判断(诚实讨论)
- **`/spec` 产物不是 PRD,也不该是。** 它是**薄的、探针背书的"决策/约束/已验证真相"脊柱**(线以上);
  PRD 是另一个高度(功能/流程/交互/逐功能验收),**厚**。二者是上下游,不是替代。
- **怎么施工**:中小项目可 SPEC.md → 代码(R 的验收=施工目标,门绿灯=CI 漂移探测);大项目需要
  中间层(设计/任务)——正是当初为极简砍掉的 OpenSpec proposal/design/tasks,留下了 **Gate 1.5 空缺**。
- **漂移**:**任何厚散文文档都会漂**;`/spec` 对漂移的回答=权威层做薄 + 探针可执行(漂了能探测)+
  CLAUDE→SPEC 收口 + 重跑对账。**推论:真正会漂的正是那份厚 PRD**——所以别把它供奉成真实源。
- **reframe(真相持久度分层)**:`SPEC.md`(最持久)/ 代码+测试(持久)/ 详细计划·PRD(低,**一次性
  重生,别供奉**)。漂移源恰恰是被供奉的中间层。

### 3. 用户拍板:A(我推荐)
加一个下游技能 **`/build`(Gate 1.5)**:读 `SPEC.md` → **临时**生成 design+tasks → 施工 → 以

## 第 19 轮 · 2026-07-02 — 真实用户反馈:`cmd.exe` 一句话装进了 PowerShell,直接报错

用户在真实 Windows 机器上执行了第 18 轮给出的 `cmd.exe` 一句话安装命令,**贴到了 PowerShell 里**,
完整报错回执如下:`&&` 被判定为"不是本版本合法的语句分隔符"、`curl -fsSL` 报"找不到参数 fsSL"
(说明 `curl` 被 PowerShell 的 `Invoke-WebRequest` 别名接管)、`call` 不是可识别命令、`%TEMP%` 没有
被展开(被当成字面路径)。这组特征**精确指向 PowerShell**,而非 `cmd.exe`——这正是我此前诚实标注
"cmd.cmd 只经审阅、未在真机验证"这一覆盖缺口暴露出的真实问题:**没验证的不只是脚本本身的语法,
还有"用户实际所在的 shell 是否等于我假设的 shell"这个更基本的前提。**

### 1. 根因判断:名词判断偏了("Windows" ≠ "cmd.exe")
现代 Windows 开发者的默认终端(Windows Terminal、VS Code 内置终端等)**绝大多数场景下都是
PowerShell,而非传统 `cmd.exe`**。用户最初的原话是"Windows cmd/Linux bash",但真实触达用户的
"Windows"这一类目,其**实际所指**更多是 PowerShell。这是又一次"先定义名词、再谈动词"式的教训:
之前只按用户的字面措辞("cmd")去实现,没有反问"用户真正会用哪个 shell"。

### 2. 修正:新增原生 PowerShell 安装器,而非仅仅"写清楚说明"
没有满足于"在文档里加一句提示区分 shell"这种表面修补,而是补上**真正原生的 PowerShell 安装器**
`scripts/install.ps1`,用业界该场景的标准范式 `irm <url> | iex`(Scoop、rustup 等装机脚本同款
写法):
- 全程只用 PowerShell 5.1+ 内置能力(`Invoke-WebRequest` + `Expand-Archive`),`git` 不可用时
  **零外部依赖**回退,不像 `cmd.exe` 版本依赖 `tar.exe`。
- 有意**不设**全局 `$ErrorActionPreference = 'Stop'`,因为 `git clone` 的常规进度信息走 stderr,
  若与该设置叠加容易把"正常进度输出"误判成终止性错误(PowerShell 已知的老坑)——改用 `*>` 这种
  纯流重定向操作符处理 `git`,只对真正的 PowerShell cmdlet(`Invoke-WebRequest`/`Expand-Archive`/
  `Copy-Item`)显式加 `-ErrorAction Stop`。
### 3. 用户当场追加指令:干脆不要 cmd 批处理了
用户看到修正方向后,直接给出更彻底的定案:**Windows 一律用 PowerShell 写 `.ps1`,不要再维护
`cmd.exe` 批处理**;安装指示应该是**用 `powershell.exe` 去执行这个 `.ps1`**——而不是要求用户先
自行判断"我现在是不是在 PowerShell 里"。

这个方案**从根上解决了本轮问题**,而不只是"文档里提醒一下":`powershell -NoProfile
-ExecutionPolicy Bypass -Command "irm <url> | iex"` 这条命令本身**显式调用 `powershell.exe`
可执行文件**,不管使用者当前贴到 `cmd.exe`、PowerShell、"运行"对话框还是某个 `.bat` 文件里,
它都会正确进入 PowerShell 执行——**彻底消除了"用户搞不清自己在哪个 shell 里"这一类问题的存在
条件**,比"给两条命令、让用户自己选对"更根本。落地:删除 `scripts/install.cmd`;`README.md`
Windows 一节收敛为这一条命令;`install.ps1` 头部用法说明同步为"经 `powershell.exe` 从任意 shell
调用"为主、"已在 PowerShell 提示符下则可直接 `irm|iex`"为辅。

### 4. 诚实边界(延续)→ 已由用户真机验证闭环
本沙箱依旧没有 Windows 环境,也尝试过安装 PowerShell(GitHub Release 制品被环境代理拦截、
apt/snap 均不可用)——**`install.ps1` 当时是审阅而非实测**,已用括号/引号配平等静态检查降低风险,
但覆盖限度如实标注,并请用户在真机复核这次修正。
