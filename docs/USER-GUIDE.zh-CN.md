## 1. 五分钟上手

### 1.1 安装(一句话)

```powershell
# Windows(任意 shell 里粘贴都行,它会显式调起 PowerShell)
powershell -NoProfile -ExecutionPolicy Bypass -Command "irm https://raw.githubusercontent.com/suifei/spec/main/scripts/install.ps1 | iex"
```
```bash
# Linux / macOS / WSL / Git Bash
curl -fsSL https://raw.githubusercontent.com/suifei/spec/main/scripts/install.sh | bash
```

在目标项目根目录跑这一行,会往 `.claude/` 里装入两个 skill(`spec`、`build`)和两个
斜杠命令(`/spec`、`/build`)。不碰你的 `CLAUDE.md`、`SPEC.md`、`.spec/`——那些是
`/spec` 首次运行时自动生成的,属于你的项目。

### 1.2 第一次调用

在 Claude Code 里,不管你手头有什么——一个模糊的想法、一段已有代码、一份别人写的 PRD——
直接说:

```
/spec 我想做一个xxx
```

或者干脆什么都不加,只打 `/spec`,它会自己判断当前状态该干什么(见第 2 节)。它不会
立刻开始写代码,也不会立刻抛一堆问题给你——它会先自己去"侦察"(读你指的材料、搜索
知识、必要时探测环境),然后向你汇报"我理解的核心问题是什么、哪些已经想清楚了、哪些
还没有",最后**只在真正需要你拍板的地方**才提问。

### 1.3 一句话讲清楚二者的分工

| | 干什么 | 产出 | 什么时候用 |
|---|---|---|---|
| **`/spec`**(Gate 1) | 把一个模糊想法收敛成一份**可行、诚实、有证据**的规格契约 | `SPEC.md` + `.spec/`(门、知识、决策日志) | 项目起步时;想法有实质变化时;要澄清"这东西到底是什么/能不能做"时 |
| **`/build`**(Gate 1.5) | 读 `SPEC.md`,临时生成一份施工计划,写代码,用重跑的门收口 | 你的产品代码 + 测试 | `SPEC.md` 已经封存(至少某个阶段已闭环)之后,要真正开始写代码时 |

**先 `/spec`,后 `/build`。** `/build` 从不自己决定"要不要做";它只负责"`SPEC.md`
说要做的东西,怎么正确地做出来"。

## 2. 使用时机:什么时候该调用它

这是本手册最实用的一节——不是原理,而是"我现在该不该敲这条命令"的判断依据。

### 2.1 该调用 `/spec` 的五种时机

| 场景 | 你会说的话(示例) | `/spec` 会做什么 |
|---|---|---|
| **项目从零开始** | "/spec 帮我做一个能自动写周报的工具" | 先侦察(搜同类产品、搜你环境里的线索),提炼核心问题,给你一份 Phase 1 spec |
| **手头有份模糊材料** | "/spec 看看这份 PRD,帮我梳理清楚" | 读材料、找里面没想清楚的地方、标出闭环/未闭环,而不是照抄 |
| **一个新想法冒出来** | "/spec 我们还想加个多用户支持" | 判断这是否突破当前 spec 的边界;若是,开一个新阶段(不覆盖旧阶段) |
| **你怀疑某个假设是错的** | "/spec 我们真的能在浏览器里跑原生 git 吗?" | 去研究、去探测,给你一个诚实的答案(哪怕答案是"不行") |
| **代码写着写着,发现和 spec 对不上了** | "/spec 我们发现 xxx 其实做不到,得重新想想" | 承认旧阶段的决定有问题,开新阶段并显式声明"推翻了阶段 N 的第几条" |

### 2.2 该调用 `/build` 的时机

只有一种:**`SPEC.md` 里有一个已经闭环(或至少门已经绿灯)的阶段/需求,你要真正开始写
代码了。**

```
/build 把 Phase 1 的需求实现出来
```

`/build` 会先告诉你它准备怎么做(临时生成的计划),你确认后再动手写代码,写完用门探针
重新验证一遍,红了就不算完成。

### 2.3 不需要调用它的时机(这点同样重要)

- **纯粹的实现细节调整**——换个变量名、调个 UI 间距、优化一段算法——这些在"spec 线"
  以下,`/spec` 根本不管,你直接改代码就行。这不是它偷懒,是它的设计原则:spec **只管
  契约面**,细节的自由度必须还给你和执行 agent。
- **常识性的环境检查**——这个端口通不通、这个目录能不能写——不该问它,也不该让它
  为这种事立"门"。它自己内部也严格遵守这条(见 2.4)。
- **你已经很确定答案、只是想让 AI 干活**——比如"帮我把这个函数重构成异步的"——直接说
  就行,不需要走 `/spec` 这套收敛流程,那是"施工"层面的事,该找普通的编码交互,或者
  `SPEC.md` 已经封存后走 `/build`。

### 2.4 一张决策表(遇事不决,查这个)

| 你面临的情况 | 该做什么 |
|---|---|
| 这个改动会不会**改变行为、契约、依赖的技术选型、或某个已声明的约束**? | 会 → `/spec`;不会 → 直接改代码 |
| `SPEC.md` 还没有,或者当前想法它满足不了 | `/spec` |
| `SPEC.md` 已经封存了一个阶段,要开始写这部分代码 | `/build` |
| 施工过程中发现 spec 里的某个决定站不住脚了 | 停下,回到 `/spec`(不要在 `/build` 里私自改 spec) |
| 只是想知道某个技术能不能实现,还没想清楚要不要做 | `/spec`(它会诚实地告诉你"能"或"不能",附带证据) |

## 3. 核心原理:引擎盖下发生了什么

你**不需要**记住这一节才能用好这个 skill(这正是设计目标——"简单到不构成负担")。
但理解原理能帮你更好地判断"它为什么这样回应我""该怎么配合它"。

### 3.1 一个循环:侦察 → 呈现 → 提问 → 决策 → 取证 → 持久化 → 闭环

```
读 SPEC.md/STATE.md 复水 ──▶ 侦察(=研究:读材料+搜知识+探测环境)
                                    │
                                    ▼
                          呈现:核心问题是什么、哪些已闭环、哪些没想清楚
                                    │
                                    ▼
                     只问真正需要你拍板的(少问多决,见 3.3)
                                    │
                                    ▼
                       决策(能自决的自决,登记推演路径)
                                    │
                                    ▼
                    为承重的门取证(可执行探针 / 引用的权威研究)
                                    │
                                    ▼
                     写回 SPEC.md + .spec/(整份重写,不打补丁)
                                    │
                                    ▼
                    闭环(该阶段的决策全确认 + 门全绿)→ 封存
```

这个循环**每次调用只推进一小段**、每一步都把状态写到磁盘——这是为了在有限上下文里
可靠工作(见 3.6),不是随意的实现细节。

### 3.2 探真 = 研究(不是"跑个检查脚本")

"探真"这个词容易被误解成"写段代码去测"。实际上它的定义宽得多:**凡是能找到真相的
手段都算**——自己的知识、搜索全网(优先官方文档/标准机构等头部信源)、读你项目里的
代码和数据、调用可用的技能或 MCP、纯粹的推理和验算。**可执行探针只是其中最强的一种**
——专门留给"环境或行为相关、且承重"的真相。多数问题根本不需要写探针,靠研究和推理
就能定论。

### 3.3 少问多决:它凭什么替我做决定?

默认状态下,`/spec` **自己拍板**,把"为什么这么定"的推演路径记进 `SPEC.md` 的
**决策日志**,标注 `[auto]`。它只在两种情况下才真的来问你:

1. **真叉**——穷尽了所有能查的信息和推理后,依然无法确定的分歧,而且这属于价值观/
   优先级/风险偏好/商业方向这类**只有你能拍板**的判断。
2. **它发现了比你提议的更好的方案**——值得让你知道并选择。

这不是"偷懒少问",而是刻意的分工:**你的认知优势在于创造力、想象力、对核心痛点的
洞察;AI 的优势在于广度知识和把模糊判断精确分解**。让 AI 承担它擅长的,把你的注意力
留给真正只有你能做的判断。

### 3.4 门(Gate)必须承重

不是所有"确认过的事实"都值得被记录成正式的"门"。只有同时满足这三条,才配立门:
**承重**(真有决策系于它)、**不确定**(有可能是假的)、**错了有后果**(会改变设计,
而不只是实现细节)。像"这个端口是否空闲"这种常识性检查,**永远不该立门**,更不该
成为编码时要关注的重心——立门的原型是"这个方案的核心技术假设站不站得住脚",而不是
"环境够不够干净"。

### 3.5 诚实,包括说"不"

如果研究表明你的某个想法不可行,它会明确拒绝,并给出真实理由——不会为了让你满意而
悄悄按你说的做。如果你自己做的某个决定其实有问题,它也会指出来,而不是含糊带过。
这条原则甚至适用于**它自己**——如果它之前的判断错了(比如某个示例项目起点搞错了),
它会显式记录"这个结论被推翻了,原因是……",而不是悄悄改掉假装没发生过。

### 3.6 文件系统即记忆

它从不假设自己能在一次对话的上下文里"记住"整个项目。**状态全部写在磁盘上**
(`SPEC.md` 本体 + `.spec/STATE.md` 进度账本 + `.spec/knowledge/` 侦察成果缓存)。
每次调用先读这些文件"复水",搞清楚上次进行到哪一步、接下来该做什么。这意味着:
- 换一次对话、上下文被压缩、甚至隔了一周才回来接着做,都能无缝续上。
- 你随时可以打断它——它总是安全地停在"已经写盘"的状态,不会半途而废丢东西。

### 3.7 产物语种:只问你一次

第一次为你的项目生成 `SPEC.md` 时,它会问你**一次**——报告和规格文档用什么语言写
(默认是你当时用的语言,可选主流语言)。答案会被钉进 `SPEC.md` 头部,**此后永远不再
问**,不管你哪次对话用中文哪次用英文。想换,直接明说即可。

### 3.8 `/build` 的关键原则:施工计划是"用完即弃"的

`/build` 从 `SPEC.md` 读需求后,会**临时生成**一份设计/任务计划——但这份计划**不会
进版本库**,每次施工重新生成。这不是偷懒,是刻意的反漂移设计:**真正持久的东西只有
两端——`SPEC.md`(薄、有证据背书)和代码+测试(最终真相)。** 中间那份详细计划,一旦
被当成"文件"持久化保存,就会开始跟代码脱节、变成又一份没人维护的过时文档。让它"每次
重生",反而更诚实。

### 3.9 这些原理是怎么来的:skill 自己也被"探真+纠错"过

上面这几条原理不是一次性凭空定好的,而是这个 skill **自己被用户用同一套纪律不断纠偏**
出来的结果——每一条都对应一次真实的返工,完整记录在 `docs/DESIGN-NOTES.md`。简述
四次关键纠偏,方便你理解"为什么是这几条,而不是别的":

1. **"少问多决"从哪来:** 早期版本几乎每个技术选型都要停下来问用户,用户指出这违背了
   "人类只脑暴决策"的初衷——如果什么都问,人类的负担并没有真正减少。于是收敛为"默认
   自决 + 只在真叉/更优方案时才问"。
2. **"门要承重"从哪来:** 早期的示例项目把"Node.js 是否安装""端口是否空闲"这类常识
   也立成了正式的门,用户直接指出这毫无决策价值——"我们不是围绕端口是否可用编程的"。
   于是收敛出立门三准则(承重∧不确定∧错了有后果)。
3. **"先定义名词,再谈动词"从哪来:** 一次真实的设计错误——第一版"网页版 Claude Code"
   的方案直接讨论"要不要建 agent 后端",完全没先搞清楚 Claude Code 本身是什么。这次
   公开的自我纠错(4.2 节详述)之后,才把"先确立主体"升级成一条通用规则。
4. **"诚实"从哪来:** 用户问"这是真的技能测试跑出来的吗",逼出一次坦白——早期示例是
   按规则手写的模拟产物,不是真正调用技能跑出来的。承认之后,才有了后面"少问多决"和
   "诚实到敢说不"两条原则的强化版,以及第一次真跑的技能验证案例(4.1 节)。

**这件事本身也是一条最佳实践的示范:** 连这套方法论的设计过程,都经受住了它自己提倡的
纪律——有证据(决策日志)、可追溯(append-only)、犯错不遮掩(supersede 记录)。

## 4. 情景案例

以下案例分两类,**明确标注**,不混淆:
- **真实案例**——真实调用 skill 跑出来的产物,不是编的对话。其中 4.1–4.3 已在本仓库
  `examples/` 目录留档、可直接复现验证;4.4 来自一个真实的外部生产项目,因为涉及
  真实业务数据,**不进入本仓库**,本手册只引用其 `SPEC.md`/决策日志/探针证据里的
  结构化事实(数字、决策文本),不展示任何原始素材。
- **示例场景**——为讲解设计的教学性场景,标为"假设",不是真实执行记录。

### 4.1 真实案例:从"自我进化 agent 系统"这个模糊题目开始

**输入:** 用户只给了六个字——"自我进化 agent 系统",没有更多说明。

**`/spec` 做了什么:**
1. **先定义名词,再谈动词。** 没有立刻讨论"怎么实现",而是先去查权威文献(Darwin
   Gödel Machine、ADAS、自进化 agent 综述),搞清楚"自我进化 agent"这个词本身指什么。
   发现:它**不是**"让 LLM 自己改自己代码"这种直觉理解,而是一个**客观门控的
   propose→evaluate→select→archive 循环**——按可进化的层级(prompt/memory/tools/
   workflow/code/weights)分类。
2. **能自决的自己拍板**(全部记入决策日志,标 `[auto]`):循环本身该长什么样(D1)、
   必须有客观评估门拒绝退化(D2)、必须保留存档做开放式搜索而非爬坡式优化(D3)、
   自我修改必须在沙箱里做且能回滚(D4)。
3. **真叉交给用户**:通过 `AskUserQuestion` 真实提问——进化范围该多大(限定在
   prompt/memory/skills/workflow,不碰核心代码或模型权重)?晋升机制要不要人工审批
   (用户选了更激进的"自动晋升")?
4. **诚实地"硬化"了用户的选择**,而不是照单全收:用户选自动晋升后,`/spec` 没有
   简单附和,而是依据文献里"指标被钻空子是自进化系统最常见的失败模式"这一发现,
   **强制**要求补充"留出验证集评估 + 自动回滚 + 熔断开关"作为这个决策生效的前提
   (写成了正式需求 R6)。
5. **唯一的行为探针**放在最关键的不变量上:客观评估门确实能拒绝一次"回归"(注入一个
   变差的候选方案,验证它被拒绝;去掉这道门再跑一遍,验证回归被放行了——这个反向对照
   证明探针真的能"变红")。

**可以查看的产物:** `examples/self-evolving-agent/SPEC.md`(决策日志、门、需求全部
可查)、`examples/self-evolving-agent/.spec/probes/G2-evolution-gate.sh`(那个探针,
可以直接跑)。

**这个案例教你什么:** 一句话的模糊想法足够作为输入起点——不需要你先想清楚细节。
但如果你有明确的偏好(比如这里的"自动晋升"),它会尊重你的选择,同时诚实指出代价
并要求配套的安全措施,而不是简单地"你说了算,照办"。

### 4.2 真实案例:一次公开的自我纠错("Web 版 Claude Code")

**输入:** "做一个 Claude Code 的网页版本。"

**第一版(v1)犯的错:** 直接跳到"要不要建一个 agent 后端、用什么沙箱方案"——完全
没有先搞清楚 **Claude Code 本身是什么**。这是一个真实发生过的缺陷,被用户当场指出:
"你搞不清楚目标是人还是猴子,就先谈怎么生孩子、孩子叫什么名字。"

**纠正后的第二版(v2):** 先去查官方文档,确认 Claude Code 本质是一个**agentic
CLI**——终端运行、Unix 可组合、已经内置了 headless 模式和 Agent SDK,agent 循环/
工具/权限本来就在 CLI 里面。一旦这个前提确立,正确方案自然浮现:"网页化" = **接管
这个 CLI 进程的标准输入输出、经 WebSocket 转发到浏览器**——而不是重新发明一个 agent。

**`SPEC.md` 里怎么记这次纠错:** Phase 1 明确写着 "**supersede v1 的错误框架**",
连同错误的原因一起记录下来,而不是悄悄把旧内容删掉。

**这个案例教你什么:** 如果你看到 `/spec` 的第一版结论有明显的方向性错误,**直接
指出来**——它会真去研究、真去纠正,并且诚实地把"曾经错在哪"留在记录里,而不是假装
从一开始就是对的。这也提示你:**当你自己提出一个方案时,先问一句"我真的搞清楚这东西
本质是什么了吗",往往能省下后面推翻重来的成本。**

### 4.3 真实案例:本仓库自己的 `/build` 设计过程(自举)

**背景:** 用户问了一个很实际的问题——"没有真正的 PRD,AI 怎么施工?会不会又造出一份
会漂移的文档?"

**`/spec` 的回应(不是"直接同意再加个功能"):** 先明确判断——`SPEC.md` 的产出**不是**
PRD、不该是,它是薄的"决策与可行性契约"。真正会施工用的详细计划,应该是"每次重新生成
的临时脚手架",而不是又一份供奉起来的常驻文档——**被供奉的中间层,恰恰才是真正的漂移
源**。给出三个方案(A. 加一个临时计划的 `/build`;B. 做一份常驻 PRD;C. 什么都不加靠
施工 agent 自己猜),用户选了 A。

**先定义名词,再实现:** 在真正实现 `/build` 之前,先去调研业界头部方案(GitHub
Spec Kit、AWS Kiro),发现它们都把中间层持久化入库——团队据此做了一次**有意的行业
背离**,并诚实标注代价(放弃可审计的任务轨迹,用决策日志+git 历史+测试代码兜底)。

**这个案例教你什么:** 面对"这东西到底有什么用"这类质疑性问题,`/spec` 不会用套话
搪塞,而是给出一个可以被反驳、有真实取舍的判断,并且愿意基于用户的选择把缺口真的补上。

### 4.4 真实案例:一个真实生产项目的完整弧线(跨平台 OCR 指标提取)

> 与前三个案例不同,这是一个**真正投入生产使用**的项目——通过 Claude Code CLI 实际调用
> 本 skill,在开发者自己的机器上跑出来的。项目名为 media-ocr,本手册按敏感数据处理原则
> 只引用其 `SPEC.md`/决策日志/探针证据里的**结构化事实**,不展示任何原始截图。它同时
> 验证了前面讲的四条原则,是目前最完整的一份真实证据。

**核心问题:** 从多个自媒体平台(视频号、B 站、头条)的视频截图里,自动提取播放量/点赞/
分享/收藏/评论这五项互动指标,输出成结构化 JSON。约束很硬:**不依赖 GPU,纯 CPU 推理**
——这排除了大多数深度学习方案。三个平台的 UI 布局、数字格式(纯数字 vs "21.6万")、
标签形式(文字 vs 图标)全不一样,且同一平台在不同截图里指标完整度还会变。

**第一次假设,被真实探针推翻:** 团队最初选择纯 OCR 方案(RapidOCR,CPU 友好、体积小),
基于"标签词典匹配 + 位置启发式"的思路做提取。两个门给出了诚实的结论:
- **门 G3**(RapidOCR 在 16 个真实样本上的整体匹配率)—— **39.6%**,远低于预期。
- **门 G4**(纯文本 OCR 在"图标为主"平台上的表现)—— 对纯图标指标(点赞/分享/收藏/
  评论,只有 ❤️/↗/⭐/💬 图标、没有文字标签)的提取率是 **0%**——这是一个**不可逾越的
  天花板**,不是调参能解决的问题。同时,一条此前的假设("数值最大的就是播放量")也被
  真实数据推翻:低流量样本里播放量可能只有 1 或 2,根本不是最大值。
- 这正是第 3.4 节讲的"门的原型"——**能推翻一个此前认定合理的假设、改变技术方向**的,
  才配叫门。这里的门确实做到了。

**基于证据转向,再用新证据验证:** 团队据此把技术路线**倒过来**——不再让 OCR 当主力,
改成 **VLM(视觉语言模型)当主路径,OCR 降级为备用路径**。选型是 Qwen2.5-VL:3B(GGUF
量化,约 2.9GB),通过 `llama-cpp-python` 在进程内直接推理,不依赖 Ollama 等外部服务。
转向之后,专门为这个新方案又开了一道新门——**G5**,要求全字段匹配率 ≥ 85%:
- 结果:**87.5%(42/48),PASS。** 相比转向前的 39.6%,提升 **+47.9 个百分点**。
- 证据里连**怎么调都记录在案**:第一轮 Prompt 是 81.2%,第二轮把"这是这条视频自己的
  数据,不是旁边推荐视频的"和"0 也是一个有效值,不要当成缺失"这两点说清楚后,涨到
  87.5%——这本身就是"把模糊判断分解成精确指令"的一次具体示范。

**"少问多决"在真实项目里的真实比例:** Phase 3 一共产生了约 20 条决策,记在同一份决策
日志里。粗略数一下标注:**约 13 条 `[auto]`**(OCR 引擎选型、数字归一化规则、两阶段
架构拆分、多条被证据推翻后的自动修正……),**约 7 条 `[human]`**——而且这 7 条无一
例外,都是**只有人能拍板的判断**,不是技术细节:接口形式选 HTTP API、精度策略选"宁可
返回 null 也不猜错"、要不要支持相机拍照这种更麻烦的输入类型、VLM 技术路线本身、模型
文件怎么分发到生产环境(NFS + k8s Volume 挂载)、以及下面这条关于诚实的例子。

**诚实原则在生产工程里的样子:** 本地开发时,预编译的 `llama-cpp-python` Windows 版因为
用了 AVX-512 指令集,在开发者的 CPU 上直接崩溃。团队先用了一个**战术性绕过方案**——本地
跑一个独立的 HTTP 服务进程(决策 D25)。但这明显偏离了"内嵌推理、无外部服务"的原始设计
意图。几天后,用户直接决定**统一收回**:Windows 从源码编译、关掉 AVX-512,所有环境都用
同一种内嵌模式。这个决定被记成 **D27,并显式标注"supersedes D25"**——旧决策没有被
悄悄抹掉,而是留在日志里,连同"为什么当初要那样做、后来为什么改回来"的完整理由。

**这个案例教你什么(全部四条原则的一次合练):**
- **探真=研究** 不是走过场——16 个真实样本的特征分析(不同平台指标完整度、数字格式、
  标签形式)是后续每一个技术决策的地基。
- **门要承重** 在这里体现得最彻底——G3/G4 不是摆设,它们真的推翻了第一个技术方案。
- **少问多决** 的比例是真实可数的,而且问到的每一条都确实是价值判断,不是技术细节。
- **诚实** 不只是"敢说不",也包括"敢承认一个临时妥协该被收回"——D25→D27 就是证据。

### 4.5 示例场景(教学用途,非真实执行记录):项目中途冒出一个新想法

> 以下是一个**假设场景**,用来说明"阶段涌现"机制怎么运作,不是真实的执行记录。

假设你已经用 `/spec` 把一个"个人待办事项工具"的 Phase 1 定好了并封存——单机、本地
存储、无账号体系。几周后你说:

```
/spec 我们想加个多设备同步
```

`/spec` 会:
1. **先侦察**:读现有 `SPEC.md`,判断这个诉求是否已经被 Phase 1 覆盖——显然没有
   (Phase 1 明确"无账号体系"是 out-of-scope)。
2. **判断这是否跨越 spec 线**:多设备同步涉及新的真值源(要不要账号体系?数据一致性
   模型?)、新的契约(同步 API),显然跨线——需要走完整的 `/spec` 闭环,而不是直接
   开始写代码。
3. **开一个新阶段(Phase 2),而不是改写 Phase 1**:Phase 1 的内容原样保留、只读;
   Phase 2 里如果推翻了 Phase 1 的某条决定(比如"数据只存本地"这条现在要改),必须
   显式写"supersede Phase 1 的第 X 条",附带理由。
4. 走一遍正常的侦察→决策→取证流程(比如需要研究几种同步冲突解决策略,提出推荐,
   识别出"要不要支持离线优先"这种只有你能拍板的真叉)。

**这个场景教你什么:** 你不需要提前规划"项目分几个阶段"——阶段是**想法自然演进**
的副产物,不是你要预先设计的东西。你只管在有新想法时说出来,阶段划分是它的工作。

### 4.6 示例场景(教学用途):`/build` 施工中发现 spec 站不住脚

> 同样是**假设场景**,说明 `/build` 遇到"spec 与现实冲突"时的正确处理方式。

假设 `SPEC.md` 里锁定了一条决策:"用某个第三方 API 做地理编码"。`/build` 施工到一半,
发现这个 API 早已停止服务。正确的行为**不是**:
- ❌ 私自换一个替代 API,悄悄把 `SPEC.md` 里的这条决策改掉;
- ❌ 忽略这个事实,硬着头皮把代码写完然后报"完成"。

而是:**停下来,把冲突原样汇报,交还给 `/spec` 去重新决策**(可能需要重新做一轮依赖
选型的侦察——搜同类服务、给出推荐、你来拍板或授权 `/build` 按推荐自决)。这保证了
`SPEC.md` 里的每一条决策,要么是真实成立的,要么被诚实地标记为"已被推翻"——不会出现
"文档说的和代码做的不一样,但没人知道"这种情况。

## 5. 使用策略与最佳实践

### 5.1 起手式:不用想清楚细节,但要说出真实的驱动力

给 `/spec` 的第一句话,**不需要**是一份完整需求文档。一句话、一个模糊的痛点、甚至
一段别人写的、你自己都没读透的 PRD,都是合格的起点——它会主动去侦察、去补全。但
**越接近你真实的驱动力(为什么要做这件事,而不是表面在做什么),它找到核心问题的
效率就越高**。"我想做个待办工具"不如"我经常在多个设备间漏看任务,想要个不用记住
开哪个 app 的东西"有效——后者直接暴露了核心痛点,省去它反复"元问题"式追问的成本。

> **media-ocr 印证:** 起手式甚至可以是一句带着硬约束的话——"提取互动指标,但不许用
> GPU"。这一句里的"不许用 GPU"直接排除了一整类深度学习方案,比事后再纠正省得多。

### 5.2 面对提问:只回答它真正问的,不用代它操心它自己能查的

它只会在真正需要你的价值判断时才提问,而且会带着上下文和推荐选项——**你不需要
"猜它想听什么答案"**,如实说出你的偏好和顾虑就行。如果你在赶时间,直接说"你决定
吧,给个直接答案",它会切换到"直给"模式而不是继续走苏格拉底式提问。

> **media-ocr 印证:** "要不要支持相机拍照这种更麻烦的输入类型""模型文件怎么分发到
> 生产环境"——这类问题背后往往有你才知道的约束(团队有没有 k8s、能不能接受额外的预
> 处理成本),照实回答就好,不用猜"标准答案"是什么。

### 5.3 面对拒绝或质疑:提供新证据,而不是要求它"配合一下"

如果它基于研究/探针明确告诉你某个想法不可行,**说服它的正确方式是提供它可能遗漏的
新证据**(比如"其实我们内部有个私有的替代方案""这个限制在新版本里已经解除了"),
而不是简单地重复要求。它的判断是基于证据的,新证据自然会改变结论;单纯的坚持不会。

> **media-ocr 印证:** 当纯 OCR 方案被 G3/G4 两道门证明"图标平台提取率 0%"时,正确的
> 反应不是要求"再想想办法凑合用 OCR",而是接受这个证据、换技术路线——事实证明,换路线
> (VLM)之后同一批样本的匹配率从 39.6% 直接跳到 87.5%。**证据是用来换方向的,不是用来
> 说服自己将就的。**

### 5.4 团队协作场景:把 `SPEC.md` 当成协作契约,而非某个人的私有笔记

`SPEC.md` + `.spec/` 是要提交进版本库的。团队场景下的实践建议:
- **谁都可以调用 `/spec`**,但决策日志会诚实记录"谁在什么时候基于什么证据做了什么
  决定"——这天然形成了可审计的协作记录,不需要额外开会同步"我们当初为什么这么定"。
- **新成员上手时,先读 `SPEC.md`,而不是问同事。** 这正是 `CLAUDE.md` 顶部权威声明
  存在的意义——它是团队里"新真相"和"AI 产出"共同的先读文档。
- **PR 审阅 `SPEC.md` 的变更时,重点看决策日志和门的状态**,而不是逐句校对散文
  措辞——它本来就是一份"决策契约",不是要打磨文笔的产品文案。

> **media-ocr 印证:** D25(本地临时用 HTTP 服务器绕过一个 Windows 底层 bug)到 D27
> (统一收回、改成源码编译)之间隔了几天——这正是"决策日志天然形成可审计协作记录"的
> 真实样子:后来者不需要再问"为什么本地和生产环境跑法不一样",日志里写得明明白白。

### 5.5 何时该主动打断它、介入进度

- 侦察阶段读了太久、或者你发现它去研究了一个明显偏题的方向——直接打断纠正,它会
  调整并继续,不会因为被打断而丢失已有进度(状态在磁盘上)。
- 它给出的"核心问题"理解明显偏了——直接说清楚你的真实意图,不用担心"已经聊了这么
  多不好意思推翻"——它会诚实地根据新信息重新收敛。

> **media-ocr 印证:** 头条平台一开始被假设为"至少有播放量+评论两项",几天后加进来
> 4 个新样本,发现全部只有播放量——用户没有阻止这次假设被推翻,而是任由 `/spec` 把
> 旧假设标记失效、用新证据重新收敛(决策 D15)。**打断/介入不是为了让它"听话",是为了
> 让它掌握更接近事实的信息。**

### 5.6 案例复盘:一张表看懂 media-ocr 怎么印证了每一条原则

如果你只记得住一件事,记住这张表——它把第 3 章的抽象原则,和 4.4 节里发生过的真实
事情,一一对应起来:

| 抽象原则 | media-ocr 里的真实样子 |
|---|---|
| 探真 = 研究 | 先分析 16 个真实样本的平台/格式/完整度特征,再决定技术路线,不是先拍脑袋 |
| 门要承重 | G3/G4 真的推翻了"纯 OCR 够用"这个假设(图标平台提取率 0%) |
| 少问多决 | 约 20 条决策里约 13 条 `[auto]`,7 条 `[human]`——问到的都是真判断,不是凑数 |
| 诚实,包括说"不" | 证据面前不将就(转向 VLM),临时妥协也不隐瞒(D25→D27 显式 supersede) |
| spec 线(只管契约) | `SPEC.md` 记的是"选了 VLM、为什么、准确率多少",不是 Python 函数怎么写 |
| 临时计划、用完即弃 | `.spec/plan/phase3-ocr-tool.md` 是施工时生成的脚手架,权威永远是 SPEC.md |
| 文件系统即记忆 | 项目跨越多次真实的 Claude Code 会话,靠 `.spec/STATE.md` 断点续跑;甚至借助了 Claude Code 自身的跨会话记忆目录(`memory/`)索引探针结果,两套"记忆"自然重合 |

## 6. 反模式:常见的用错方式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| **把 `SPEC.md` 当 PRD 写,塞进功能清单和 UI 细节** | 违反"spec 线"——细节会让文档迅速漂移,也会让 AI 把力气花在不该管的地方 | 只记决策/契约/门/边界;细节交给 `/build` 临时生成或直接交给执行 |
| **对着常识性检查(端口/目录/工具是否存在)让它"立门"** | 常识没有决策价值,立门会污染真正承重的信号 | 顺手验一下可以,但绝不写成正式的门 |
| **每次代码要改动就先问它** | 违反"少问多决";线下(实现细节)的改动本就不需要它介入 | 只在真正跨越 spec 线(改变行为/契约/依赖/约束)时才找它 |
| **它拒绝了某个想法,反复要求它"配合一下就好"** | 它的拒绝基于证据,反复施压不会改变证据本身,只会削弱这套机制的价值 | 提供新证据,或者接受这个判断、调整方向 |
| **`/build` 施工中手动改 `SPEC.md` 让探针"过关"** | 破坏了"证据非杜撰"的根基,`SPEC.md` 从此不再可信 | 遇到 spec 与现实冲突,老老实实退回 `/spec` 重新决策 |
| **把 `/build` 生成的临时计划当成文档保存进仓库** | 违反"计划临时化"设计,重新制造漂移源 | 让它保持临时;需要审计轨迹就看决策日志 + git 历史 + 测试 |
| **多个人同时对同一个未闭环的阶段各自调用 `/spec`,互不通气** | append-only 的设计假设"读了最新状态再决策";并发冲突它处理不了 | 团队场景下,同一阶段的推进串行来,或至少先同步一下 |

## 7. 背后的工程思想

这一节回答一个更根本的问题:**当 AI 可以写几乎所有代码的时候,这套设计到底在解决
什么问题、体现了什么样的软件工程思想?**

### 7.1 AI 写代码之后,真正稀缺的是什么

在"AI 能写代码"这件事已经基本解决之后,项目失败的原因很少再是"写不出代码",而是:
- 没人说得清"我们到底在解决什么问题"(表层症状被误当成核心问题);
- 一堆看似合理的技术决定,没人能追溯"当初为什么这么选、还成立吗";
- AI 生成的东西"看起来能跑",但建立在一个从未被验证过的假设上("这能在浏览器里跑
  原生 git 吗?");
- 项目文档和代码渐行渐远,最后没人再信任文档。

这四个问题,分别对应本设计的四条主线:**核心问题挖掘**(第 3.2/3.3 节的侦察-提问
机制)、**决策可追溯**(决策日志)、**可行性有证据背书**(摸排探真、门的三准则)、
**反漂移**(spec 线 + 临时计划哲学)。也就是说,**这套设计不是在优化"AI 写代码的
速度",而是在补齐"AI 写代码快了之后,人类原本靠经验和沟通兜底、现在必须显式补上的
那部分工程纪律"。**

### 7.2 与几种经典软件工程思想的关系

- **契约式设计(Design by Contract, Bertrand Meyer)**——经典理论把"前置条件/后置
  条件/不变量"写在函数、接口这个粒度上。这套设计把同样的思想**上提到项目粒度**:
  `SPEC.md` 就是整个项目的"契约",门就是它的不变量,探针就是运行时校验。
- **瀑布模型的教训,但不走向另一个极端**——瀑布模型的失败在于"前期一次性设计,无法
  应对变化"。这里用**阶段涌现**(闭环即阶段,不预先规划)+ **已封存阶段绝对只读**
  的组合,既保留了"重要决策先想清楚"的纪律,又不假装能一次性预见所有需求变化。
- **敏捷/精益的教训,但守住一条底线**——敏捷方法论强调"避免过度文档化"，这套设计
  完全认同,但补上了一条敏捷经常缺失的纪律:**契约层面的决策仍然需要显式记录和验证**
  ——"我们决定用 X 数据库,因为 Y"这种话不能只存在于某次站会的口头讨论里。
- **持续集成/自动化验证优于人工评审**——探针纪律(反向对照、门必须能"变红")本质是
  把 CI/CD 那套"自动化验证优于人工签字"的思想,应用在**规格正确性**这个此前极少被
  自动化验证的层面。传统项目里"这个方案可行吗"往往靠开会拍脑袋决定;这里要求给出
  可执行的证据。
- **真相的持久度分层(这套设计特有的贡献)**——`SPEC.md`(最持久、探针背书)、
  代码+测试(持久、真实行为)、详细施工计划(刻意易变、用完即弃)。多数方法论要么
  把所有文档都当"应该长期维护"(导致文档腐烂),要么走向"文档不重要,代码即真相"
  的另一个极端(导致决策失忆)。这里的答案是:**只让真正承重的那一层长期存在,其余
  的坦然承认它会变、并且设计成"变了也没关系"。**

### 7.3 人机分工的重新定义

传统软件工程里,人类承担从需求分析到编码实现的几乎全部认知劳动,工具只是辅助
(IDE、编译器、测试框架)。AI 辅助编程的早期阶段("vibe coding"),分工变成"人类
描述意图,AI 生成实现"——但这种模式下,**项目的"权威"是脆弱的**:今天让 AI 这么
写、明天让它那么改,没有一份被诚实维护、有证据背书的文档说得清"我们到底决定了什么、
为什么"。

这套设计提出的分工是:

| | 人类 | AI |
|---|---|---|
| 核心价值 | 创造力、想象力、对痛点的洞察、价值判断 | 广度知识、精确分解、证据收集、执行 |
| 在 `/spec` 里的角色 | 提出真实驱动力;在**真叉**上拍板;审阅决策日志 | 侦察、研究、把模糊判断分解成可评估的选项、诚实呈现证据、能自决的自决 |
| 在 `/build` 里的角色 | 审阅计划、批准提交 | 生成临时计划、写代码、用重跑的门证明"完成"是真的完成 |

**人类从"逐行决定怎么写"退到"定义什么是对的、在无法用证据判定的地方拍板";
AI 从"辅助打字的工具"升级为"能做研究、能自我纠错、能诚实说不的分析与执行者"。**
这不只是效率提升,而是一次角色的重新分配——而这次分配能否成立,完全取决于 AI
这一侧是否真的做到"诚实、有证据、可追溯",这也是为什么本设计把"探真=研究、
门要承重、诚实到近乎苛刻"这几条,而不是"响应更快、代码更多",作为最优先的原则。

## 8. 速查附录

### 8.1 命令速查

```
/spec                                   # 复水并继续/开始
/spec 一个模糊的想法或痛点               # 带新想法调用,自动判断新建/更新阶段
/spec 看看这份 PRD/仓库,帮我梳理清楚    # 指向材料,触发侦察
/build                                  # 复水并继续施工
/build 把 Phase N 的需求实现出来        # 指定施工目标
```

### 8.2 核心术语

| 术语 | 一句话解释 |
|---|---|
| Gate 1 / `/spec` | 产出可行、诚实、有证据的规格契约 |
| Gate 1.5 / `/build` | 从规格施工出代码,计划临时化、门收口 |
| 探真(=研究) | 用一切手段找真相;可执行探针只是其中一种 |
| 门(Gate) | 承重∧不确定∧错了改变设计,才配立门 |
| 决策日志 | `[auto]`(AI 自决)/ `[human]`(人类拍板的真叉) |
| spec 线 | spec 只管契约面,细节留给执行自由变动 |
| 阶段(Phase) | 一次闭环的产物,涌现而非预设;已封存只读 |
| 临时计划 | `/build` 每次重新生成的施工计划,不入库 |
| Artifact language | `SPEC.md` 头部钉住的产物语种,问一次不再问 |

### 8.3 一分钟自检:我现在该用哪个?

```
我要做的事,会不会改变行为/契约/技术选型/已声明的约束?
├─ 会 ──▶ SPEC.md 里有对应的封存阶段吗?
│         ├─ 有 ──▶ /build
│         └─ 没有/不完整 ──▶ /spec
└─ 不会 ──▶ 直接改代码,不需要它
```
