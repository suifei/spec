## 摘要

本项目要回答一个具体问题:**能否把"项目从一个模糊想法到一份可信、可施工的规格说明书"这一过程,
封装成一个像 `/init` 一样简单、可反复调用的 Claude Code 命令?** 答案是 `/spec`——一个让 AI 扮演
"需求收集专家"的单一指令,以及它的下游伙伴 `/build`——一个从规格构造代码、但拒绝把施工计划变成
新的漂移源的"Gate 1.5"命令。

这份报告记录三件事:**为什么要做**(动机与痛点)、**怎么做的**(调研与设计原则)、**中途改了什么、
为什么改**(17 轮讨论中的关键决策与几次自我纠偏)。它是诚实的——包括承认早期示例是"手搓模拟"而非
真跑、承认第一版语言规则有缺陷、承认某个示例一开始就搞错了研究的起点。这种诚实本身,也是设计的
一部分:见第五章"三次概念级纠偏"。

## 第一章 研究背景与核心动机

### 1.1 起点:从 OpenSpec 的启发,到彻底重新设计

项目最初的动机是研究 [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec) 这类
"规格驱动开发(Spec-Driven Development)"项目的核心 pipeline(提示词、agent 逻辑、schema),
将其转化为 Claude Code 原生 skill。第一版实现忠实移植了 OpenSpec 的多命令生命周期
(`explore → propose → apply → verify → archive`),并附带一套脚手架脚本与模板。

但这个第一版很快被用户**推翻**——不是因为实现有 bug,而是因为**命令本身的定位就不对**。用户提出
的核心质疑是:

> "我需要的 `/spec` 是一个就像 Claude Code `/init` 这样的命令——只有一个,人类只负责脑暴和决策,
> AI 做所有重活。"

这是整个项目最重要的一次转向:从"移植一套完整的规格驱动工作流"变成"设计一个单一、可重复调用的
函数"。此后所有讨论都在这个约束下进行。

### 1.2 核心痛点清单

综合用户在各轮讨论中提出的诉求,可以提炼出以下几类真正驱动设计的**痛点**:

| # | 痛点 | 对应的设计回应 |
|---|------|----------------|
| P1 | 现有规格驱动工具**命令太多**(explore/propose/apply/verify/archive),操作与认知负担高 | 收敛为单一命令 `/spec`(D-01, D-12, D-19) |
| P2 | 团队用 AI 工具开发项目,但**没有一个收口闸**去把控"项目该是什么"这件事 | `/spec` 定位为过程管理的 **Gate 1** |
| P3 | 传统规格文档(PRD/设计文档)**会漂移**,和代码渐行渐远,失去权威性 | 探针驱动的"契约面 spec"+ 后续"临时计划"哲学(第八章) |
| P4 | AI 生成的"真值源/门"**可能是编出来的**,不可信 | 摸排探真(D-05, D-06);门必须能"变红"(反向对照) |
| P5 | 长流程可能跑到一半**上下文爆掉**、换会话就断片 | 文件系统即记忆 + `.spec/STATE.md` 进度账本(D-27) |
| P6 | AI 提问方式生硬、教条,像审讯或问卷 | 侦察-提问引擎(D-21~D-24),低负担、可应对性提问风格 |
| P7 | 项目会反复重构(UI 调整、语言迁移),spec 如果管得太细,**天天要改** | "spec 线"——只管契约面,不管实现细节(D-13) |
| P8 | AI 容易为了"完成任务"而**迎合不合理的想法**,不敢说"不行" | 诚实底线原则(D-36),可拒绝并给出真实理由 |
| P9 | AI 容易把探针滥用成"什么都要立门"(连端口是否可用都要立门) | "门必须承重"三准则(D-33) |
| P10 | AI 容易"没搞清楚是什么就直接谈怎么做" | "先定义名词,再谈动词"(D-39) |
| P11 | 项目做完 spec 之后,**AI 到底怎么施工**?会不会又制造一份会漂移的 PRD? | 补 `/build`(Gate 1.5),施工计划**临时化**、不入库(D-40, D-41) |
| P12 | AI 用中文对话,但报告应该用哪种语言,应不应该跟着对话语言漂? | Rule 0:产物语种"问一次、钉死、不再问"(D-43, D-44) |

这份清单不是预先规划出来的,而是**在 17 轮真实讨论中逐步浮现的**——这本身也印证了项目的一条核心
设计哲学:**阶段是闭环涌现的,不是预设的**(D-09)。

## 第二章 相关工作调研

按照项目自身"探真=研究"的纪律,设计过程中多次主动调研了同类工具,而不是闭门造车。

### 2.1 OpenSpec(项目的初始参照系)

多命令生命周期(explore/propose/apply/verify/archive),change 维度的 delta 规格
(ADDED/MODIFIED/REMOVED/RENAMED)。**局限**:没有多层级治理方案,没有 AI 主动发现真值源的机制,
没有摸排探真(验收全靠人工判断"看起来对不对")。这是本项目决心"彻底重新设计,不是简单改名"的
直接原因(用户原话:"彻底点,放手")。

### 2.2 GitHub Spec Kit 与 AWS Kiro(第 15 轮,`/build` 立项前的调研)

在设计 `/build`(Gate 1.5)之前,团队专门研究了业界两个头部的"规格驱动构建"工具:

- **GitHub Spec Kit**:`constitution`(项目宪法)+ `/specify → /plan → /tasks → /implement`,
  每个阶段产出一份**入库提交**的 markdown 产物。
- **AWS Kiro**:`requirements.md → design.md → tasks.md`,存于 `.kiro/specs/`,**版本控制**,
  外加 `steering/` 目录承载团队共享的项目上下文。

**关键发现**:业界两个领先方案都**把中间层(计划/设计/任务)持久化入库**,作为构建阶段的真实源。
这个发现直接催生了本项目一次**刻意的背离**——详见第八章。这正是"先定义名词,再谈动词"原则在
`/build` 设计上的应用:先搞清楚"构建层"在业界通常长什么样,再决定我们要不要跟随。

### 2.3 Darwin Gödel Machine 与 ADAS(为验证"自进化 agent"示例而调研)

在真实调用 `/spec` 技能(而非手搓示例)测试"自我进化 agent 系统"这一课题时,调研了
Darwin Gödel Machine(Sakana AI / UBC / Vector Institute, 2025)与 ADAS / Meta Agent Search
(ICLR 2025)。这次调研的价值不在于最终架构,而在于**纠正了一个常见误解**:"自进化 agent"不是
"LLM 自己改自己",而是一个**客观门控的 propose→evaluate→select→archive 循环**。这是"先定义名词、
再谈动词"原则的又一次真实验证(见第九章)。

### 2.4 Claude Code 官方文档与 ttyd/wetty(为纠正"Web 版 Claude Code"示例的错误而调研)

第一版"Web 版 Claude Code"示例直接跳到"建 agent 后端 + 沙箱",完全没有先去查 Claude Code 官方
文档确认它本质是什么。用户当场指出这个缺陷后,团队补做了调研:Claude Code 官方文档确认其为
**agentic CLI**(终端运行、Unix 可组合、headless `stream-json`、Agent SDK,agent 循环/工具/
权限已内置);此外调研了 ttyd / wetty / xterm.js 这类"终端上 web"的成熟范式。结论:
"Web 化" = 接管 CLI 的标准 I/O、经 WebSocket 转发到浏览器,而不是重建一个 agent。这次调研直接
产生了一条**通用技能级规则**(见第九章第三节)。

## 第三章 设计目标与指导原则(定稿版)

综合 12 轮以上讨论收敛出的核心原则,最终固化进 `SKILL.md` 的非负原则包括:

1. **文件系统即记忆,上下文是一次性的**——状态全部外置到磁盘,每次运行先"复水"。
2. **探真 = 研究**——用一切手段找真相(自身知识、全网、项目数据、skill、MCP、深度推理),
   可执行探针只是其中一种(且最强的一种)手段,不是探真的定义。
3. **少问多决**——默认 AI 自己决定并登记推演路径,只有两种情况才问人类:(a) 穷尽一切来源与推理
   后依然无法定夺的真叉(价值/优先级/风险/商业取向);(b) AI 发现了比人类提议更优的方案。
4. **证据,绝不造假**——任何有分量的结论都要有真实依据(引用研究或可执行探针),没准备好就不建。
5. **诚实到近乎苛刻**——研究证明不可行就明确拒绝并给出真实理由;人类的决议若有问题也要指出来,
   绝不为了让人满意而附和明知错误的东西。
6. **门必须承重**——只有"承重 ∧ 不确定 ∧ 错了会改变设计"的真相才配立门;常识性检查(端口是否
   空闲、目录是否可写)绝不能成为门,更不能成为编码关注的重心。
7. **spec 只管契约面**——行为能力、契约接口、真值源与门、可度量的非功能需求、显式声明的约束;
   实现细节永远留给执行层自由变动。
8. **一份完整文档**——`SPEC.md` 整体重写,不碎片化。
9. **不施工**——`/spec` 只定规格、验证就绪状态,不写产品代码(这是留给 `/build` 的边界)。

以及一条**最高优先级、凌驾于以上所有原则之上**的规则(第十章详述):**产物语种是一次性钉住的
选择,问一次,永不再问。**

## 第四章 设计演进的时间线(17 轮讨论的主题化梳理)

原始讨论记录按时间顺序逐轮展开(见 `DESIGN-NOTES.md`),本报告按**主题**重新归纳为五个阶段,
便于理解决策的因果链条:

### 阶段一:定位重构(第 1—2 轮)
从"重型阶段状态机(依赖图、触发器、locked/provisional 双标签)"收敛为"最小化 + 单一不变量"——
**已封存阶段绝对只读,新阶段只能追加并显式声明否定了哪一条**。阶段不再是人类预先规划的,而是
"闭环"这一事件的**副产物**:每达成一次闭环,就诞生一个新阶段。

### 阶段二:反漂移机制(第 3—4 轮)
提出"spec 线"概念,解决"项目会反复重构,spec 会不会天天要改"的痛点——spec 只管契约面,
实现细节的自由度完全保留,靠**探针的双重身份**(闭环时的取证 + 之后 CI 里的漂移检测)来维持
契约不被违反。随后发现"探针可能是空洞的绿灯"(比如拿 `npm test` 当门探针,而测试本身写得毫无
意义)这一致命漏洞,提出"反向对照"作为普适铁律:**任何探针都必须能演示自己的失败模式**。

### 阶段三:角色与协议细化(第 5—9 轮)
明确 spec 的管控应该"按高度"而非"按主题"分层;真值源应由 AI **主动勘探**而非只靠人类申报;
`/spec` 应作为"人类决策前的侦察兵"——取证求真是 AI 的纪律,拍板 GO 是人类的决策权;融合用户
此前的"认知伴飞(Cognitive Copilot)"提问哲学,但只迁移哲学、不迁移其 PKM 专用机器;新增
`.spec/knowledge/` 持久化侦察成果避免重复探索;最后补上最关键的可靠性闭环——
`.spec/STATE.md` 进度账本,解决"长流程 + 有限上下文"的可靠执行问题。

### 阶段四:概念纠偏(第 10—13 轮)
详见第五章、第九章——这是整个项目里**最重要的自我修正阶段**:时间维度做减法(砍掉过度设计的
"新鲜度阈值")、纠正"探真被窄化成 check 脚本"、纠正"任何常识都被立成门"、纠正"AI 动不动就问
人类"、纠正"没先搞清楚主体是什么就直接谈方案"。

### 阶段五:能力补全与收口(第 14—17 轮)
诚实交代此前示例是手搓模拟并第一次真跑技能;讨论 `/spec` 产物对下游开发的真实价值,补齐
`/build`(Gate 1.5)并完成仓库自举;新增并修正产物语种规则。

## 第五章 三次概念级自我纠偏(第 11—13 轮)

这三次纠偏值得单独成章,因为它们不是"新增功能",而是**发现并纠正了此前设计中的概念混淆**——
这恰恰体现了"诚实"原则不只是对用户诚实,也包括对自己此前的错误诚实。

### 5.1 纠偏一:"探真"被窄化成了"跑脚本"

早期实现里,"摸排探真"逐渐被理解为"写一个 shell 脚本去检查"。用户指出这是概念上的窄化:
**探真(探寻真相)和发现知识是同一件事**——凡是能找到真相的手段都算数:自身知识、全网搜索、
项目本地数据、可用的 skill、MCP、深度推理与验算。可执行探针只是其中"最强的一种"(对环境或行为
相关的真相给出最硬的证据),**绝不是探真的定义**。落地为原则 2:"探真 = 研究"。

### 5.2 纠偏二:任何常识都被立成了"门"

早期的示例项目(游戏 demo)里,"Node.js 是否安装""端口是否空闲""资源目录是否可写"都被立成了
正式的"门"。用户直接点出这毫无意义:**这类常识性判断没有决策价值,我们不是围绕"端口是否可用"
来编程的。** 由此确立"立门三准则"——必须同时满足**承重**(真有决策系于它)、**不确定**(可能
为假)、**错了有后果**(会改变设计而非实现细节)。原型案例是游戏 demo 里的 G0:探针推翻了
"这个项目要用 Godot 原生构建"的假设,**直接改变了技术路线**——这才配做门。

### 5.3 纠偏三:AI 动不动就把决策丢给人类

早期设计里,几乎每一个技术选型都会走"呈现选项 → 请人类决策"的流程,这与用户"人类只负责脑暴和
决策,AI 做所有重活"的初衷背道而驰——如果什么都要问,人类的负担并没有真正减少。用户澄清:
**默认应该是 AI 自己拍板并把推演路径记录下来**,只有两种情况才真正需要问人类:(a) 穷尽所有
信息来源和推理后依然无法确定的真叉(这是价值观/优先级/风险偏好/商业方向层面的判断,只有人类
能拍板);(b) AI 发现了比人类原本设想更优的方案,值得让人类知情并选择。这条原则连带催生了
`SPEC.md` 新增的"决策日志"章节,每条决策标注 `[auto]`(AI 自决)或 `[human]`(人类拍板的真叉),
使得"AI 到底替我做了哪些决定"完全可审计。

**这三次纠偏共同指向同一个更高层的定位澄清**(第 11—12 轮):`/spec` 的本质是让 AI 扮演
**需求收集专家**,与用户一起把模糊的想法收集、澄清、组织、标准化成一份可行的规格——这个角色
同时覆盖了市场分析、需求调研、头脑风暴、可行性分析、技术架构、设计评审等多个传统职能,AI 在
每个职能上知识不够就主动去研究补齐。

## 第六章 "先定义名词,再谈动词"(第 13 轮)——一次示例暴露的技能级缺陷

这是整个设计历程中,**由一个具体错误直接倒逼出通用规则**的典型案例,值得单独展开。

### 6.1 错误是怎么发生的

在制作"Web 版 Claude Code"示例时,第一版 spec 上来就讨论"要不要建一个 agent 后端、用什么沙箱
隔离方案"——完全没有先去确认 **Claude Code 本身是什么**。用户的原话精准地指出了问题的本质:

> "你搞不清楚目标是人类还是猴子,你先去谈如何生孩子,孩子叫什么名字?这是一个非常非常明显的缺陷!"

### 6.2 纠正后的正确路径

真正去查 Claude Code 官方文档后发现:它本质是一个 **agentic CLI**——在终端运行,遵循 Unix
可组合哲学(可以被 pipe、可以在 CI 里跑、可以被链式调用),已经内置了 headless 模式
(`claude -p --output-format stream-json`)和 Agent SDK,agent 循环、真实工具、权限模型全部
已经存在于 CLI 内部。一旦确立了这个"是什么",正确的方案自然浮现:**"Web 化"的本质是接管这个
CLI 进程的标准 I/O(交互式 PTY,或 headless 的 `stream-json`),经 WebSocket 转发到浏览器**——
这是终端上网(ttyd / wetty / xterm.js)领域已经成熟的范式,而不是重新发明一个 agent。

### 6.3 上升为技能级规则

这次纠错没有止步于"改好这一个示例",而是被提炼为一条**通用规则**,写入 `SKILL.md` 的调查步骤
首条与 Guardrails:**在讨论任何解决方案之前,必须先用权威/官方信源确立"这个东西本质是什么、
基本原理是什么"**——起点错误比细节错误严重得多。示例本身也被重做为 v2 版本,**诚实记录了
v1→v2 这次纠错**(Phase 1 显式声明"supersede v1 的错误框架"),而不是悄悄改掉、假装从未犯过错。

## 第七章 诚实原则的两次深化(第 12、14 轮)

### 7.1 诚实底线:可以拒绝,可以指出问题

用户明确要求:AI 不能为了迎合用户不合理的想法(经研究和外部知识分析根本不可能实现的事)而不
拒绝;对用户自己做出的决议,如果有问题,也要诚实指出、不能掩盖事实;**可以合理拒绝,并给出真实
理由**。"明知是错的、却选择舒适地附和"被明确定性为一种失职。

### 7.2 诚实交代:承认早期示例不是"真跑"

这条原则最有说服力的一次自我应用发生在第 14 轮。用户直接问:"这是真正的 skill 测试跑出来的
么?" 诚实的回答是**不是**——早期的两个示例项目是团队"按 skill 的规则手写"出来的示范产物:
探针是真跑的、网络调研是真做的,但**没有真正调用 `/spec` 技能去驱动整个流程**,其中的"人类
决策"环节也是团队代写的。这正是"诚实原则"在实践中最直接的一次自我检验——发现问题就承认,
而不是含糊其辞。承认之后,团队立刻用 `Skill` 工具**真正调起** `/spec` 技能,跑出了第一个
"自我进化 agent 系统"的真实示例(详见第九章)。

## 第八章 `/spec` 产物的定位之辩:它是不是 PRD?(第 15 轮)

这是本报告要重点呈现的一次**方法论层面**的讨论,直接回应了"这个 spec 到底有什么价值、AI 靠
它怎么施工"的核心疑问。

### 8.1 用户提出的疑问

> "这个产物对后续开发的意义和价值是什么?没有真正的 PRD 设计,AI 如何施工?这个对产出 PRD
> 有价值么?PRD 会不会漂移?"

### 8.2 判断:`SPEC.md` 不是、也不应该是 PRD

团队的回应是明确的:`/spec` 的产出**不是** PRD、功能清单或完整的施工蓝图,而是一份
**"决策与可行性契约"**——只装载"线以上"的东西:项目本质是什么、真正的可行性(探针验证过的
真相)、不可轻易推翻的决定(决策日志)、边界与反模式。它故意做得很薄。

这引出了一个更深的判断,即**"真相持久度分层"**模型:

```
SPEC.md(最持久)        —— 决策/约束/已验证真相,薄、探针背书
      ↕
代码 + 测试(持久)      —— 真实行为的最终真相
      ↕
详细计划 / PRD(易变)  —— 应该是"一次性重生的",绝不应该被供奉成常驻真实源
```

**关键洞察**:任何厚的、散文式的详细计划文档都会漂移;真正会漂移的,恰恰是被供奉成"真实源"的
那份厚文档。如果把详细 PRD 当真实源持久化入库,就是在制造一个漂移源——这与 `/spec` 全程秉持
的"反漂移"设计哲学(spec 线、探针可执行、CI 漂移检测)恰好背道而驰。

### 8.3 三个方案,用户选择方案 A

针对"AI 到底怎么施工"这个真正的缺口,团队提出三个选项供用户决策(这正是"少问多决"原则里
第二类应该问人类的情形——**AI 发现了一个更好的选项,值得让用户选择**):

| 方案 | 描述 | 取舍 |
|------|------|------|
| **A(推荐)** | 新增 `/build`(Gate 1.5):读 `SPEC.md` → **临时**生成设计/任务计划 → 施工 → 以"需求验收 + 门绿灯"收口;计划不入库、用完即弃 | 漂移最小,与 `/spec` 一贯哲学一致 |
| B | 做一份常驻的 PRD/设计层(类似 OpenSpec 的 proposal/design/tasks,入库版本控制) | 细节最全,但要自己承担漂移风险,需要额外配探针/对账机制 |
| C | 什么都不加,靠施工 agent 每次自行从 `SPEC.md` 推导 | 最省事,但大型项目容易失控 |

用户选择了 **A**。团队的判断依据是:方案 A 本质上是把 PRD"从一个名词(被供奉的文件),变成一个
动词(每次重新生成)"——既补上了"AI 怎么施工"的缺口,又没有把漂移源重新请回来。

### 8.4 `/build` 的设计:一次刻意的行业背离

在真实调用 `/spec` 为 `/build` 立规格时(仓库自举——本仓库自己的 `SPEC.md` 就是这次真跑的产物),
团队先去调研了业界头部方案(GitHub Spec Kit、AWS Kiro),发现二者**都把中间层(计划/设计/任务)
持久化入库**。团队判断这是一次**有意的背离**,而非疏忽,并在文档中诚实标注了背离的代价:
放弃了一份"可审计的任务执行轨迹",用决策日志 + git 历史 + 测试代码作为替代的兜底记录。

`/build` 的核心不变量最终固化为:

1. **权威 = `SPEC.md`,`/build` 只能遵从、绝不能篡改**——出现冲突就停下来交还给 `/spec` 去
   重新决策,绝不私自改 spec 去让施工过关。
2. **计划是临时的**——每次重新生成,存放在 `.gitignore` 排除的暂存目录,绝不作为真实源提交。
3. **"完成"由重新跑一遍门探针来判定**——不是"看起来写完了"就算数;这条不变量本身也被写成了
   一个真实的可执行探针(G2:对比"重跑门判定完成"与"不重跑门、只看文件是否存在"两种做法,
   后者会把一个门是红的坏实现误判为"已完成"——证明前者才是必要的)。

### 8.5 最终澄清:正名而非改动

用户后续追问"到底建不建 PRD",团队给出的最终结论是:**保持现状(不建持久化 PRD)是对的判断**,
唯一需要补的是**在文档里把 `SPEC.md` 的定位说清楚**——它是"决策与可行性契约",不是功能清单。
这条澄清后来被一字不差地放进了 `SPEC.md` 模板、`README.md`、`SKILL.md`、`CLAUDE.md` 四个地方,
确保任何读到这些文档的人第一时间就不会误会。

## 第九章 首次真实调用技能验证(第 14 轮)

### 9.1 为什么"手搓示例"是不够的

早期的两个示例("nebula-drift"游戏 demo、"web-claude-code"知识密集型 demo)虽然探针是真跑的、
研究是真做的,但整个"人类决策"环节是团队代写、模拟出来的——这在方法论上是有缺陷的,因为它
**无法证明技能本身真的可执行**,只能证明"如果照着规则手写,产物会长这样"。

### 9.2 真跑:自我进化 agent 系统

团队用 Claude Code 的 `Skill` 工具真正调起 `/spec` 技能,让技能的指令**实际驱动**整个流程,
课题选为"自我进化 agent 系统"(用户建议的新课题,理由是这个课题更能检验 AI 自身知识库和外部
知识分析检索的真实水平)。这次真跑的产出包括:

- **先定主体**:调研自进化 agent 的权威综述文献与 Darwin Gödel Machine、ADAS 等具体系统后,
  确立核心问题不是"LLM 自己改自己",而是一个**客观门控的
  propose→evaluate→select→archive 循环**——按可进化的"层级"从浅到深排列为
  prompt/memory/tools/workflow/code/weights。
- **可自决的部分自动登记**:循环本身、客观评估门、archive 机制、沙箱与回滚——这四项决策全部
  由 AI 自主拍板并记录了推演依据(标注 `[auto]`)。
- **真叉真的交给了用户**:通过 `AskUserQuestion` 工具真实提问,用户选择了进化范围(限定在
  prompt/memory/skills/workflow,不碰核心代码或模型权重)与晋升机制(**自动晋升**——这是
  比推荐选项更激进的选择)。
- **诚实"硬化"了用户的选择,而不是照单全收**:针对用户选择的"自动晋升"这一较激进的机制,
  团队没有简单附和,而是依据文献里"客观指标被钻空子(Goodhart)是自进化系统最常见的失败模式"
  这一发现,**强制**要求补充"留出验证集评估 + 自动回滚 + 熔断开关"作为该决策生效的前提条件。
  这是"诚实原则"在真实决策场景下的一次具体应用——尊重用户的决定权,但不因此放弃指出真实风险
  的责任。

## 第十章 产物语种规则的两版迭代(第 16—17 轮)

这是整个设计历程里**耗时最短、但迭代质量很能说明问题**的一条规则,值得完整呈现其"提出 → 
发现缺陷 → 修正"的全过程,因为它本身就是"少问多决"原则的一次现身说法。

### 10.1 第一版(第 16 轮):跟随人类当前输入语种

用户最初的要求是:**用人类输入的语种创建报告**——人类用阿拉伯语,报告就该是阿拉伯语;人类用
英文,就该是英文;若既有版本语种不一致,主动翻译一遍(大 spec 可迭代分块翻译)。这条规则被
定为**最高优先级**,写入 `SKILL.md` 的 "Rule 0"。

### 10.2 缺陷浮现:语种会漂移

用户很快指出第一版的问题:**"我用中文来决策 spec,但我希望输出报告是面向全球的英文版本。"**
如果规则是"永远跟随当前对话使用的语言",这个诉求根本无法满足——更严重的是,这意味着产物语种
会**随着每次对话使用的语言而漂移**,与整个项目"反漂移"的核心设计哲学自相矛盾。

### 10.3 第二版(第 17 轮):问一次、钉死、不再问

用户提出的修正方案,恰好完美契合项目已有的"少问多决"原则:**产物语种本身就是一个人类偏好/
价值判断,不是 AI 能推导出来的**,理应归入"真叉"的范畴——**该问,但只问一次**。修正后的规则是:

- **首次落盘前问一次**:默认值 = 人类当前正在使用的语言;附带主流人类语言选项(英文、中文、
  日文、西班牙语、阿拉伯语等)供选择。
- **答案钉进 `SPEC.md` 头部**,格式如"Artifact language: English — pinned 2026-07-02"。
- **钉住之后永不再问**——之后任何一次 `/spec` 或 `/build` 调用只读这个钉住的值,无论那次对话
  人类实际打的是什么语言;人类若想更改,必须**显式说明**("以后用日文写"),这会触发重新翻译。
- **`/build` 自己绝不询问语种**,只读 `SPEC.md` 里已经钉住的值——这也维护了 `/build` "Gate 1.5、
  只施工不做决策"的边界。
- **兼容早于本规则存在的旧项目**:若发现 `SPEC.md` 已存在但从未钉过语种,就从既有文档的语言
  静默反推、记录钉住,不追加提问——依然是"零提问路径",不是例外情形。

本仓库自身的 `SPEC.md` 已按此规则补上了首个真实的钉住记录:`Artifact language: English —
pinned 2026-06-30(declared: global open-source audience; not re-asked)`。

## 第十一章 诚实的自我评估:局限与开放问题

按照第 5 章确立的"诚实"原则,这份报告也应该如实呈现设计本身尚未解决、或者依赖判断力而非
机制保证的部分:

1. **"承重判断"依赖分析者的水平**。门是否该立,取决于分析者能否准确识别"真正承重"的点;
   三准则能约束纪律,但不能替代判断力——一个经验不足的使用场景仍可能规格不足或过度规格化。
2. **`SPEC.md` 是"已验证之真的下界",不是正确性证明**。单个探针的空洞可以靠反向对照堵住,
   但"是否探全了"这件事本身不可证明——绿色看板不应被过度信任。
3. **`SPEC.md` 单凭自身无法直接施工一个非平凡产品**。这正是为什么需要 `/build` 在施工时
   临时补齐细节——`SPEC.md` 只提供骨架,不提供全身。
4. **临时计划(ephemeral plan)牺牲了可审计的任务执行轨迹**,这是"反漂移"这一目标必须付出的
   真实代价,用 Decision Log + git 历史 + 测试代码作为替代兜底,而非无成本的选择。
5. **"spec"这个名字本身容易引起误解**——大多数人听到"spec"会联想到功能级的 PRD/SRS,而实际
   产出更接近"决策/可行性契约(charter/constitution)"。这个误解已经通过在多处文档中加入明确
   澄清来缓解,但命名本身带来的第一印象偏差仍然存在。
6. **研究类结论都是"截至某个时间点"的**——尤其是快速演进的领域(如自进化 agent、Claude Code
   自身的能力),需要在真正施工前重新核实。这也是"时间维度"原则(第 10 轮)要求所有记录都必须
   携带真实 OS 时间戳的原因。

## 第十二章 结论与展望

`/spec` 与 `/build` 的设计历程,本质上是一场**持续的自我纠偏过程**——项目多次在"看起来已经
做得不错"的节点上被用户的一句追问打回重做:从"多命令生命周期"到"单一函数",从"探针=脚本"到
"探真=研究",从"什么都立门"到"门必须承重",从"AI 什么都问"到"少问多决",从"没搞清楚是什么就
谈方案"到"先定义名词、再谈动词",从"手搓模拟示例"到"真实调用技能",从"跟随对话语言漂移"到
"问一次、钉死、不再问"。

这些纠偏共同的底色是同一条原则:**诚实——包括对用户诚实,也包括对自己此前的判断诚实**。项目
没有掩盖任何一次错误的第一版设计,而是把每一次纠错都完整记录进 `docs/DESIGN-NOTES.md` 的决策
日志(D-01 至 D-44),供后来者审视这些判断是如何形成、又是如何被推翻或修正的。

当前状态:`/spec`(Gate 1)与 `/build`(Gate 1.5)均已实现并投入自举使用(本仓库自身的
`SPEC.md` + `.spec/` 即是产物);三个示例项目分别展示了不同侧面的能力
(`examples/self-evolving-agent/` 是唯一一次真实调用技能跑出的产物,`examples/web-claude-code/`
记录了一次公开的纠错过程)。尚未完成、留给未来的工作包括:对 `/build` 本身进行一次同等严格的
"真跑测试"(目前尚无案例证明其在真实项目上端到端可靠执行),以及持续观察"临时计划"哲学在更
大规模项目上是否依然成立。
